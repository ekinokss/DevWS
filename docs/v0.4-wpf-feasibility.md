# DevWS v0.4 WPF Feasibility Report

**Status: P2 feasibility spike — experimental evidence, not production acceptance.**

Baseline: `release/v0.3.0-preparation` at `c8cf6dd928853f62abbe21a5b2a42f287cf4c09a`
(the P1/P1-A contract merge). This spike is isolated under `spikes/v0.4-wpf/`.

This report evaluates WPF/.NET as the foundation for the v0.4 visual workspace editor. It
is based on a standalone prototype under `spikes/v0.4-wpf/`, measured on the P2 host. It
does not implement the P1 backend, does not read or write the canonical DevWS
configuration, and does not launch or manipulate live windows.

Raw measurements are in `spikes/v0.4-wpf/results/`. The scripts that produced them are in
`spikes/v0.4-wpf/tools/`.

## 2. Prototype architecture

`spikes/v0.4-wpf/DevWS.WpfSpike.csproj` is a standalone WPF application with no third-party
packages.

| Component | Role |
| --- | --- |
| `CanvasTransform.cs` | World ↔ screen transform, fit, zoom-at-pointer, pan, clamping |
| `WorkspaceCanvas.cs` | Custom `FrameworkElement` rendering monitors, work areas, items, selection, grid, labels; mouse/keyboard interaction |
| `FixtureModels.cs` | Synthetic JSON fixture schema and loader |
| `MainWindow.xaml` / `.cs` | Fixture selector, monitor/item lists, numeric geometry editor, status |
| `App.xaml.cs` | Startup, self-test, benchmark, interaction-benchmark, snapshot modes |
| `IntegrityProbe.cs` | Token integrity-level query |
| `GeometrySelfTest.cs` | Deterministic transform and fixture tests |
| `Fixtures/` | 2/10, 4/50, 8/200 synthetic fixtures plus a redacted host snapshot |
| `tools/` | Fixture generation, read-only host topology export, startup and publish measurement |

The canvas uses:

```text
screen = (world - virtualScreenOrigin) * zoom + pan
world  = (screen - pan) / zoom + virtualScreenOrigin
```

`world` is the DevWS backend virtual-screen coordinate space. WPF device-independent pixels
are only the drawing surface; `scalePercent` is displayed as a label and is not used in the
transform.

The prototype was launched through `explorer.exe` so it inherited the interactive user's
medium token. Benchmark logs report `integrity: Medium`; the elevated capture shell was not
used to run the app directly.

## 4. Startup and memory benchmarks

Startup results use the medium-integrity Explorer launch. Each fixture has one first run plus
ten repeated process launches. `processReadyMs` is from process start to the canvas-ready
point; `canvasReadyMs` is from app startup to the same point.

| Fixture | First process | Repeated process median (min–max) | Canvas median (min–max) | Idle WS median (min–max) |
| --- | ---: | ---: | ---: | ---: |
| 2 monitors / 10 items | 787.4 ms | 756.55 ms (736.6–815.4) | 674.65 ms (657.4–712.8) | 136.96 MB (136.48–137.34) |
| 4 monitors / 50 items | 767.7 ms | 777.80 ms (749.6–816.4) | 686.90 ms (668.6–725.5) | 141.22 MB (123.25–142.68) |
| 8 monitors / 200 items | 766.4 ms | 759.25 ms (745.4–825.2) | 678.95 ms (668.0–711.7) | 143.34 MB (124.57–144.18) |
| Host snapshot (2/4) | 949.1 ms | 790.2 ms (single run) | 730.2 ms | 138.43 MB |

The first run is not proven to be a genuinely cold OS-cache startup. The host snapshot first
run was slower, but the test did not flush the OS cache; it is labeled **first observed
run**, not cold-start evidence.

Interaction benchmark (120 zoom/pan frames, transform + layout loop):

| Fixture | Elapsed median | CPU delta median | WS delta median | Total WS median |
| --- | ---: | ---: | ---: | ---: |

## 5. Geometry and DPI observations

### Deterministic geometry self-test

`--self-test` passed **10/10**:

- negative-origin fit;
- world → screen → world round trip;
- zoom-at-pointer anchor invariance;
- pan round trip;
- item rectangle round trip;
- zoom clamping;
- all four fixtures fit inside the viewport (2/10, 4/50, 8/200, host).

Raw: `results/self-test.json`.

### Rendered canvas

An in-app `RenderTargetBitmap` snapshot of the 4-monitor/50-item fixture showed:

- four monitor rectangles in correct relative positions;
- negative X/Y origins (`virtualScreenRect = -1920,-1080,4480×2520`);
- dashed work-area boundaries inside each monitor;
- 50 item rectangles inside the work areas;
- selected-item highlight.

Raw observation: `results/visual-verification.json`. The snapshot itself was not committed.

### Real-host DPI

The host has two 100% monitors. WPF reported `DpiScaleX=1.0`, `DpiScaleY=1.0`, primary
screen 2560×1440, matching the DevWS primary monitor rectangle. The host topology virtual
screen is 4480×1440, matching the fixture. No coordinate discrepancy was observed at 100%.

### Mixed DPI and negative physical origins

- **Mixed-DPI physical test: NOT EXECUTED.** Both host monitors are 100%.
- **Negative physical monitor origin: NOT EXECUTED.** The host secondary is at positive
  (2560,355); negative origins are synthetic.
- The synthetic 2-monitor fixture labels a 150% monitor, but that is a fixture label, not a
  physical DPI measurement. The canvas does not use `scalePercent` for geometry.

The contract remains correct for synthetic negative origins; physical mixed-DPI behavior
requires P10 hardware/guest evidence.

## 6. Accessibility findings

UI Automation inspection of the 8-monitor fixture found 88 descendants and named controls for the fixture selector,
monitor list, item list, X/Y/W/H editors, Apply button, and canvas. List items now expose
their display text through `ToString()` rather than the CLR type name.

Verified through UIA:

- non-mouse item selection via `SelectionItemPattern.Select` (item-001 → item-002);
- numeric editing via `ValuePattern.SetValue` on the X editor (-1512 → 123);
- keyboard-focusable list, edit, and button controls;
- a named custom canvas pane.

**Keyboard keystroke test: NOT EXECUTED.** Synthetic keystrokes from the elevated automation
shell were not reliably delivered to the medium-integrity WPF window. The standard WPF
ListBox/TextBox/Button controls are keyboard-focusable, and the canvas handles arrow-key
nudges in code, but a direct keystroke-level pass was not captured. This is a test-harness
limitation, not evidence that keyboard operation is broken.

**Custom canvas limitation:** it exposes one named pane, not per-monitor or per-item
automation peers. The monitor/item lists plus numeric fields are the current text-based
alternative. The production accessibility design must add per-shape peers or an equivalent
accessible object model.

Raw: `results/accessibility.json`.

## 9. Recommended framework

**WPF is technically viable and is the recommended framework for P3, conditional on the
owner accepting its packaging cost.**

Why WPF wins on the evidence:

- It runs at medium integrity with no new third-party runtime.
- The canvas transform and synthetic geometry are correct.
- Startup is sub-second on this host; idle memory is ~137–150 MB.
- Standard WPF controls provide a usable keyboard/UIA path; the custom canvas limitation is
  known and addressable.
- It adds no new NuGet/native dependency chain to a PowerShell-centric project.

Why the recommendation is conditional:

- Self-contained WPF adds roughly **65–69 MB compressed** to the installer payload.
- Framework-dependent WPF is tiny (0.10 MB zip) but adds the **.NET Desktop Runtime 8**
  prerequisite, which the current product does not require.
- Avalonia might reduce size, but it was not measured and adds a third-party framework.

If the owner rejects the payload increase and rejects a .NET Desktop Runtime prerequisite,
run a small Avalonia P2b spike before committing to WPF.

## 10. Proposed packaging strategy

**Primary recommendation: self-contained folder deployment under the installed app root**
(e.g. `app\editor\`), embedded in the existing setup payload.

- No new runtime prerequisite.
- Predictable startup; no single-file first-run extraction.
- Folder/file manifest is straightforward and consistent with the existing installed
  `app\lib` model.
- Projected compressed payload increase: **~68.8 MB**; projected installer ~71.9 MB.

Alternatives:

1. **Self-contained single-file** — ~64.6 MB compressed, 5 files, slightly simpler manifest,
   but first-run extraction behavior and a 154 MB exe need separate acceptance.
2. **Framework-dependent** — ~0.10 MB compressed, but requires .NET Desktop Runtime 8 x64;
   only viable if the owner accepts that new prerequisite.
3. **Avalonia** — only after a measured P2b spike; do not assume its size/startup benefit.

No installer change is made in P2. The projection is a planning input, not a rebuilt
installer.

## 11. Entry criteria for P3

P3 (read-only editor backend and protocol projection) may begin only when:

1. The owner accepts the P1/P1-A contract and this P2 report.
2. The owner chooses the packaging strategy:
   - self-contained folder (recommended),
   - self-contained single-file, or
   - framework-dependent with the .NET Desktop Runtime prerequisite.
3. The owner accepts WPF for P3, or authorizes an Avalonia P2b spike first.
4. P3 implements only the read-only backend/projection (`hello`, `inspect`, `read-config`,
   `project`) and the protocol host; it does not implement `save` or GUI editing yet.
5. P3 preserves the P1 module allowlist, no-worker/no-broker boundary, and no-live-window
   behavior.
6. P3 adds deterministic tests for projection parity, `read-config` hash binding, request
   limits, and forbidden-library absence.

The six v0.3 deferred scenarios remain unqualified and are not P3 entry criteria.
