## 2. Investigation A — what does "skipped" actually require?

### 2.1 The question

P9-E recorded, for an item whose relative anchor is missing **and** whose absolute fallback is
unreachable:

- `show-layout` reported `[relative unavailable] [skipped]`;
- `ws launch` exited **1**;
- the launch printed **"was created but could not be identified"**;
- the harness window inventory found **zero** matching windows.

P9-E correctly withdrew the inference "no window was created". This investigation determines
what the product contract actually mandates, and therefore what a valid acceptance test must
assert.

### 2.2 Three distinct behaviours that must not be conflated

| # | Behaviour | What it means |
| --- | --- | --- |
| 1 | **Skipping relative placement** | The relative target is not used. A lower-precedence layer may still decide the geometry. |
| 2 | **Launching without applying geometry** | The terminal window is created normally, at its own default position; no move is requested. |
| 3 | **Refusing to launch entirely** | No window is created for the item. |

These are independent. The product implements **(1)** and **(2)**; it does **not** implement
(3) for this condition.

### 2.3 Source evidence

**`src/lib/devws-relative-layout.ps1` — `Resolve-DevWSRelativePlacement` policy header:**

```
#   - a reachable resolved target wins;
#   - otherwise use the absolute fallback only when the existing
#     reachability rule accepts it on an available topology;
#   - otherwise ApplyGeometry=false and no verified rectangle is reported;
#   - unavailable topology never advertises a fallback.
```

The terminal state for the failure case is `ApplyGeometry=false` plus *no verified rectangle*.
It says nothing about suppressing creation.

**`src/lib/devws-lifecycle-layout.ps1` — unreachable-fallback branch (line 405):**

```powershell
$metrics = Test-DevWSRectReachable -Rect $effective -MonitorRects $monitorRectValues
$apply   = [bool]$metrics.Reachable
$placementStatus = if ($apply) { "fallback" } else { "fallback-unreachable" }

if (-not $apply) {
    $warnings.Add(("$setIdValue/$itemId" + ": fallback layout is not reachable on the current monitor topology; the item will be handled normally but its window position will not be changed."))
}
```

The wording is explicit and decisive: **"the item will be handled normally but its window
position will not be changed."**

**`src/lib/devws-terminal-launch.ps1` — plan-record construction (line 990):** an item that is
not currently present is recorded in the `State = "missing"` branch **together with
`CreateArguments`**:

```powershell
$tracking = & $TrackingContextFactory $terminal
$createArguments = [string[]]@(& $CreateArgumentsFactory $terminal $tracking)
$records.Add((New-DevWSTerminalPlanRecord ... -State "missing" `
    -CreateArguments $createArguments -ApplyGeometry ([bool]$placement.ApplyGeometry) ...)) | Out-Null
```

`ApplyGeometry` is carried on the record but consumed only in the *move* step
(`if ([bool]$record.ApplyGeometry) { Move-DevWSWindowHwnd ... }`). It never gates creation.

**`src/lib/devws-launch.ps1` (lines 886–897)** — failure aggregation that produces the exit code:

```powershell
if ($null -ne $terminalFailureText) { throw $terminalFailureText }
```

`TerminalFailures` is populated from *identification/classification* failures, not from a
skipped placement. `LayoutWarnings` (which is where the skip warning lives) is merely printed:

```powershell
foreach ($warning in @($result.LayoutWarnings)) { Write-Host $warning -ForegroundColor Yellow }
```

### 2.4 Test evidence

`tests/run-tests.ps1` encodes the intended semantics directly:

- **"unreachable fallback geometry skips movement with deterministic warnings"** (line 36665)
  asserts `$slot.ApplyGeometry -eq $false`, `$slot.Reachable -eq $false`, and the exact warning
  text — the test name says **"skips movement"**, not "skips launch".
- **"matched sparse / unreachable fallback: recreate without moving"** (line 37265) asserts,
  for a **reset** of an unreachable-fallback item:
  `Assert-Equal 1 $calls.Count "unreachable fallback still resets"`,
  `Assert-Equal $false $placements[0].move "unreachable fallback requests no movement"`,
  `Assert-Contains $text "Terminal 'slot' recreated." "reset still reports success"`.
- **"relative lifecycle skips placement when relative and fallback are unreachable"** (line
  37724) asserts only `ApplyGeometry -eq $false`, `Source -eq "relative-unavailable"`,
  `PlacementReason -eq "relative-target-and-fallback-unreachable"` and a warning — never that
  no window exists.

### 2.5 Contract evidence

`docs/v0.4-visual-editor-contract.md`:

- §5.5: *"an unreachable relative target falls back only if the absolute fallback is reachable;
  an unreachable fallback is **skipped with a warning**."*
- §5.8 row *Fallback unreachable*: projection `fallback-unreachable`; **`item skipped`**.
- §8.4: the editor must show *"the skip reason when neither target is usable"*.

In every case the surrounding text is about **projection and geometry**, not about suppressing
the window. Nothing in the contract requires a launch refusal for this state. Contrast the
rows that *do* mandate refusal: **"Profile entry unreachable → profile-aware lifecycle
refuses"**. The contract distinguishes refusal from skip deliberately, and assigns refusal only
to the profile case.

### 2.6 The trace field itself settles the semantics

The single most direct piece of evidence is how the product defines its own `skipped` token in
the `lifecycle-layout-plan` trace event (`src/lib/devws-launch.ps1`):

```powershell
Write-DevWSLaunchTrace -Event "lifecycle-layout-plan" -Data ([ordered]@{
    ...
    skipped = @($frozenPlan.Items | Where-Object { -not [bool]$_.ApplyGeometry } |
        ForEach-Object { [string]$_.ItemId })
})
```

`skipped` is populated **exclusively** from `ApplyGeometry` being false. The product's own
vocabulary therefore defines "skipped" as *"no geometry applied"* — not *"not launched"*. Any
acceptance test that reads `skipped` as "no window created" contradicts the product's own
definition of the term.

**`src/lib/devws-display.ps1` states it in plain language**, in the note printed by
`show-layout` itself (line 667):

> *"Items marked [skipped] are handled without moving their windows; all other enabled items use
> the rectangles shown above."*

That is the same command whose output P9-E quoted as `[skipped]`. The help text attached to that
very marker says the window is handled and simply not moved.

### 2.7 Classification of the P9-E N2 result

| Candidate diagnosis | Verdict |
| --- | --- |
| Incorrect test expectations | **Yes — this is the primary cause.** N2 asserted "no window created, skipped as designed". The product never promised that. |
| Missing evidence for correct behaviour | **Yes, also true.** The run captured no trace, so the actual `ApplyGeometry=false` placement decision was not recorded. |
| Genuine contract/implementation mismatch | **No — not demonstrated.** Implementation, tests and contract agree with each other. |
| Still unresolved | **Not for semantics.** The *semantics* are settled by source + tests + contract. Only the *observation* remains outstanding. |

**Conclusion (Investigation A).** The required behaviour for an item whose relative anchor is
missing and whose absolute fallback is unreachable is:

1. the relative target is **not** applied;
2. the absolute fallback is **not** applied;
3. **the window is still created** and is left at its natural/default position;
4. placement is reported as skipped with a deterministic warning;
5. the launch **does not treat this as an error** — the skip is a warning, not a failure.

A launch may still exit non-zero, but only for an unrelated reason such as window
identification failure. **Exit code alone must never be used as the skip oracle.**

Therefore the assertion to test is *"the window exists and its rectangle was not moved to the
fallback rectangle"*, **not** *"no window exists"*.

> **This is a clarification of what to measure. It does not change the acceptance criterion,
> and it does not by itself upgrade N2.** N2's observation is still missing; it is now
> well-specified.

## 3. Investigation B — exact DevWS identity stability

### 3.1 Why P9-E failed to evidence it

P9-E captured Windows-level topology three times around the reconnect (`EnumDisplayMonitors`,
`EnumDisplayDevices`, `Screen.AllScreens`) but invoked the **DevWS resolver only once, after**
the reconnect. So the durable PnP instance IDs were shown stable, while the DevWS-derived
tokens were not captured on both sides.

### 3.2 The correct probe already exists

`ws monitors` is the ideal instrument and needs no new code:

- `Show-DevWSMonitors` (`src/ws.ps1`) is **config-free**: it never loads the workspace config,
  never contacts hosts, never touches windows or display settings.
- `Get-DevWSMonitorLines` (`src/lib/devws-display.ps1`) renders the **full identity token**
  (`lines += ("  id      " + $token)`), with only the *fingerprint* shortened for humans.
- It also renders `rect`, `work`, `scale` and `output`, which is exactly the monitor-rectangle
  correlation the acceptance requires.
- An incomplete identity is treated as an observed state (`exit 0`); only a failed topology
  acquisition exits non-zero.

Because it is config-free and read-only, it can be run **before any product interaction** and is
safe to invoke on both sides of a reconnect.

### 3.3 Minimal identity test design

Run the identical probe twice around exactly one controlled reconnect, and require all of the
following.

| # | Capture | Artifact |
| --- | --- | --- |
| 1 | `ws monitors` in the RDP session → **pre-disconnect** snapshot | `identity-pre.txt` + `identity-pre.json` |
| 2 | Disconnect the RDP client; confirm the session state changed in the guest | session-state log |
| 3 | Reconnect the same guest, same account, same `.rdp` | connection log |
| 4 | `ws monitors` in the new session → **post-reconnect** snapshot | `identity-post.txt` + `identity-post.json` |

Structured extraction, per snapshot: `sessionId`, `capturedUtc`, monitor `id` tokens, `rect`,
`work`, `primary` marker, `fingerprint`, and — recorded **separately** — the GDI device name
from `EnumDisplayDevices`.

Acceptance for this sub-criterion:

| Requirement | Rule |
| --- | --- |
| Identical DevWS tokens | The **set** of `id` tokens is byte-identical pre and post |
| Distinct monitors | Exactly two tokens, and they differ from each other |
| Rectangle correlation | Each token maps to the same `rect` in both snapshots (including the negative origin) |
| Timestamps | Both snapshots carry a UTC timestamp and a session id distinct from session 0 |
| GDI names | Recorded but **explicitly not required to match** — P9-E observed `DISPLAY1/2` → `DISPLAY17/18` |
| Fingerprint | Expected identical; if it differs, the topology changed and the test must be re-run rather than reinterpreted |

Only the DevWS token field is authoritative. GDI names are diagnostic and must never be used as
identity, which is precisely the property this test checks.

## 4. Investigation C — minimal combined replay design

One bounded disposable guest covering both outstanding gaps. **Not executed in this pass.**

### 4.1 Why one replay is enough

Both gaps need the same guest shape: Windows 11 Gen2 with RDP multi-monitor and the published
v0.3.0 artifact. Identity stability needs one reconnect; N2 needs one clean single-item launch.
They share the VM, the media, the activation step and the cleanup.

### 4.3 Phase ordering (deliberate)

```

P1  VM build, activation, RDP enable, product install, health check
P2  RDP session #1: two monitors, negative origin, devws tokens  -> identity-pre
```

### 4.4 N2 test design (the part P9-E got wrong)

**Fixture — exactly one item.**

```json
{
  "id": "n2-skip",
  "type": "terminal",
  "enabled": true,
  "windowId": "DevWS-n2-skip",
  "path": "C:\\Windows",
  "layout": { "x": 9000, "y": 9000, "w": 640, "h": 480 },
  "layoutMode": "relative",
  "layoutRelative": {
    "monitor": { "identity": "path:DEFAULT_MONITOR/<nonexistent-instance>" },
    "basis": "workArea",
    "rect": { "x": 0.5, "y": 0.5, "w": 0.5, "h": 0.5 }
  }
}
```

Preconditions, each verified rather than assumed:

- the canonical set contains **exactly this one** item (assert the item count);
- no pre-existing managed window: assert an empty managed-window inventory;
- anchor is genuinely absent: no monitor token matches, asserted from `ws monitors`;
- fallback `9000,9000 640x480` is genuinely unreachable on the current topology.

**Expected behaviour (from §2):** window created; geometry **not** applied; placement reported
skipped; warning emitted; the skip itself does **not** raise a failure.

**Inventory must be title-independent.** P9-E's harness matched window titles, which is why it
saw nothing. Use, in this order:

1. process-tree inventory: all descendants of the launching `ws`/broker process, with PID,
   parent PID, process name, start time;
2. `EnumWindows` over **all** visible top-level HWNDs with PID, class name and rectangle —
   matched to that process set by PID, not by title;
3. the DevWS runtime state file and the broker's own `stage2-*` records as corroboration.

**Required captures:**

| Capture | Purpose |
| --- | --- |
| `DEVWS_LAUNCH_TRACE` at **Medium** integrity | the trace gate is Medium-only; Highest runs wrote empty files in P9-E |
| `lifecycle-layout-plan` event | proves the skip decision and shows `skipped:[...]` |
| `stage2-broker-ready` / `stage2-terminal-final` | proves the broker path and whether the terminal finalized |
| exit code | recorded, but **not** treated as the oracle |
| full stdout/stderr | the exact warning and any identification message |
| pre/post HWND inventory | presence of a window, matched by PID |
| `GetWindowRect` on any created window | proves it is **not** at `9000,9000` |

**Two independently reported results.** The N2 replay yields **two separate verdicts** that must
never be collapsed into one. A geometry decision and a lifecycle-completion decision can diverge,
and a nonzero exit code alone does not prove that placement skipping failed, just as a created
window alone does not prove the installed lifecycle succeeded.

#### N2-A — Placement-skip behaviour

PASS requires **all** of:

- exactly one enabled terminal item in the set;
- its relative monitor anchor is absent from the live topology;
- its absolute fallback (`9000,9000 640x480`) is demonstrably unreachable;
- `ApplyGeometry=false` for the item and the item appears in the lifecycle trace's **skipped**
  set;
- the expected deterministic skip warning is emitted;
- a newly created terminal window is **positively attributed** to the item using
  title-independent PID/HWND evidence (pre/post process inventory with start times and parent
  PIDs, full `EnumWindows` inventory, PID-to-window correlation — never a title filter);
- the fallback rectangle was **not** applied;
- no geometry movement contrary to the skip decision is evidenced.

#### N2-B — Installed lifecycle completion

PASS additionally requires **all** of:

- successful terminal creation **and identification**;
- broker completion/finalization verified (the applicable `stage2-*` ready/final events);
- `failures=[]` or an equivalent zero-failure record;
- a successful clean single-item launch exit status;
- no unrelated terminal-identification or broker failure in the same run.

#### Combined verdict rules

| Verdict | Condition |
| --- | --- |
| **N2-A PASS** | Every N2-A condition above holds |
| **N2-A FAIL** | The window was placed at `9000,9000`; or geometry was applied contrary to the skip decision; or the warning is absent; or the trace contradicts the reported behaviour |
| **N2-B PASS** | Every N2-B condition above holds |
| **N2-B FAIL** | Creation, identification, broker finalization, or zero-failure completion did not occur for this item |
| **INCONCLUSIVE** | Instrumentation could not support a judgement: item count ≠ 1; no trace captured; inventory not trustworthy or title-dependent; window not attributable to the item; fixture invalid |

**Split reporting is mandatory.** If **N2-A passes but N2-B fails**, report exactly that split
and **do not claim the full N2 lifecycle PASS**. Conversely, if the window exists and the broker
record is clean but placement was demonstrably applied at the fallback rectangle, N2-A fails
while N2-B may still pass.

**Explicit non-assertions.** "No window was created" must not appear in either PASS criteria —
per §2 it is not the contractual behaviour. And an instrumentation failure, an unattributable
window, a missing trace, or an invalid fixture must **never** be converted into a product
failure; those are INCONCLUSIVE by definition.

Reset/refusal variant (optional, cheap): `ws reset` on the same fixture should **recreate** the
window and report success without moving it — mirroring the tested reset semantics.

### 4.5 Identity phase detail

- Both snapshots taken with the same `ws monitors` invocation, same account, same session type.
- The pre snapshot must be taken **while the first session is established**, not before
  connecting, so that RDP-provided displays are already present.
- After disconnecting, assert the guest reports the session as disconnected before reconnecting;
  otherwise the "reconnect" is not one.
- Reconnect with the identical `.rdp` file; record its hash.

| C2 VM | if the gate fails, save `DevWS-v0.3.0-C2-Acceptance-20261102` with `Stop-VM -Save` only, and restore it **mandatorily** afterwards |

### 4.7 Failure and stop conditions

Stop immediately, preserve evidence, and restore in this order if:

- the guest cannot present two monitors, or the origin is not negative;
- the DevWS tokens are not distinct;
- the token set changes across the reconnect (record as FAILED for that sub-criterion, not as a
  harness problem);
- the N2 item count is not 1, or no trace is captured → INCONCLUSIVE, not PASS;
- the C2 save cannot be verified, or any owner application closes;
- the host fingerprint or config hash changes;
- evidence cannot be archived and verified before cleanup.

## 5. Outstanding supervisor decisions

1. **N2 acceptance wording.** §2.6 concludes the P9-E expectation was wrong, not the product.
   Approving this reading is a decision about acceptance criteria, so it is escalated rather
   than assumed. Options: (a) adopt "created, not moved, skipped with warning" as the criterion;
   (b) require genuine launch refusal, which would be a **product change** and a contract change;
   (c) leave the criterion unspecified and keep N2 permanently inconclusive.
   **Recommendation: (a).** It matches implementation, tests and contract.
2. **Whether to run the replay at all.** If (b) is chosen instead, a guest run cannot settle it —
   product work would come first.
3. **Guest envelope approval** for one Gen2 VM per §4.2, including the temporary NAT step.
4. **C2 save authorisation** in the event the RAM gate fails again (it did in P9-E and will again
   unless the machine is quieter).
5. **Screenshot exception scope.** Already accepted for the placement measurement only; confirm
   it applies to this replay's N2 window evidence, where an API rectangle plus PID-matched
   inventory is the substitute.
6. **Whether the identity sub-criterion is required for full D2**, or whether distinct stable
   identifiers plus stable token derivation is sufficient. This pass does not decide it.

## 6. Judgment

**P9-F investigation: PASS** for the authorised read-only scope.

- **Investigation A: RESOLVED.** The contract, implementation and tests all require *skip
  placement, still launch, warn, do not treat as error*. The P9-E N2 expectation was incorrect;
  there is no evidenced contract/implementation mismatch. N2 becomes a **well-specified
  outstanding observation**, not an open semantic question — and it is reported as two
  independent results (placement-skip, lifecycle completion) that may diverge.
- **Investigation B: DESIGN READY.** `ws monitors` is the correct probe; a two-snapshot test
  around one reconnect with explicit acceptance rules is specified.
- **Investigation C: DESIGN READY.** One bounded replay covers both, with precise
  PASS/FAIL/INCONCLUSIVE rules, **split N2-A / N2-B reporting** (§4.4), and title-independent
  inventory.

**No status is upgraded.** E1 token stability is still NOT FULLY EVIDENCED, E2 unreachable
fallback is still INCONCLUSIVE, and full D2 installed lifecycle remains **NOT QUALIFIED**. No
product code was changed and no acceptance threshold was relaxed.
