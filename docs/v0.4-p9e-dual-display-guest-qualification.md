## 4. Gate E1 — display topology and identity: **PASS**

Client `.rdp` used:

```ini
use multimon:i:1
selectedmonitors:s:0,3
```

Local monitor IDs were re-verified as `0` (internal 1920×1080 at `2560,355`) and `3`
(external 2560×1440 at `0,0`) before the session. Listing `0` first made the physically
right-hand internal panel primary in the remote session.

### Independent confirmation

### DevWS identity tokens

DevWS's own resolver, run inside the session:

```
identity=path:DEFAULT_MONITOR/<instance-A>  rect=0,0 1920x1080        primary
identity=path:DEFAULT_MONITOR/<instance-B>  rect=-2560,-355 2560x1440
signature = path:DEFAULT_MONITOR/<instance-A>@0,0,1920x1080;path:DEFAULT_MONITOR/<instance-B>@-2560,-355,2560x1440
fingerprint = EF148B91DD07900E11002CF9AC62BC7962E61835E1670E5452114E7870790FFC
```

`identityComplete=true`, `correlationComplete=true`, `identityAmbiguous=false`.

The volatile instance suffixes are masked here as `<instance-A>`/`<instance-B>`; the full
device-instance tokens are preserved verbatim in the archived evidence
(`devws-topology.json`, `e1-topology-*.json`).

Both displays expose the same adapter class (`Microsoft Remote Display Adapter`) but
**distinct device-path instances** (`…\0001` and `…\0002`), so the identity chain yields two
distinct durable `path:` tokens.

### Identity stability across a controlled reconnect

The session was disconnected from the client and reconnected.

| Property | Before reconnect | After reconnect | Stable |
| --- | --- | --- | --- |
| Monitor device instance IDs | `MONITOR\Remote_Monitor\…\0001`, `…\0002` | **identical** | **yes** |
| DevWS `path:` tokens | `…/<instance-A>`, `…/<instance-B>` | **identical** | **yes** |
| Monitor rects | `0,0 1920x1080`, `-2560,-355 2560x1440` | identical | **yes** |

The GDI name churn is recorded deliberately: it confirms that DevWS must not and does not use

stable.

**E1 verdict: PASS** — two distinct guest monitors, a genuine negative X origin, and distinct
stable `path:` identities across a reconnect.

  geometry, so trace and measurement belong to the same launch.
- Pixel screenshots of the guest desktop could not be captured: `CopyFromScreen` returns
  blank content in this RDP session, and the host-side RDP client window was minimised by the

  an evidence gap: every acceptance criterion is measured by API, not by eye.
- The two-display layout mirrors the client's physical arrangement, so the "right-hand"
  client display became the guest's primary at the positive origin and the "left-hand" one
  took the negative origin. That is exactly the hypothesis under test.

**D2 installed lifecycle is qualified for this configuration** — RDP multi-monitor on a
disposable Hyper-V guest, with both displays provided by the remote terminal's indirect
display driver.

Two scoping notes that belong with the verdict:

1. This is **RDP-session** qualification, not physical-hardware qualification. The negative
   origin was produced by the remote display driver from the client's monitor arrangement,
   which is the mechanism P9-D hypothesised. D2's physical-hardware variant was separately
   covered for the editor layer in P9-C and remains unqualified for installed lifecycle
   placement on physical panels.
2. The two guest monitors share one adapter class and are distinguished **only** by device
   instance (`…\0001` vs `…\0002`). That is enough for identity here, but it is a narrower
   identity margin than two physically distinct panels.

D3–D6 are untouched by this pass.
