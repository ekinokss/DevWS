## 3. Protocol and limits

The backend speaks `devws-editor/1`, UTF-8 JSON Lines, one request and one response at a
time. stdout carries only protocol responses; diagnostics go to stderr.

| Limit | Value | Enforcement |
| --- | --- | --- |
| Maximum request line | 4 MiB | Chunked byte-bounded reader before accumulation; `request-too-large` and connection close |
| Maximum response line | 16 MiB | Serialized-size check; `response-too-large` fallback |
| Maximum JSON depth | 32 | `ConvertFrom-Json -Depth 32`; malformed/deep requests fail closed |
| Maximum config document | 4 MiB | Exact-byte snapshot reader; `config-too-large` |
| In-flight requests | 1 | Sequential loop; no pipelining |

Request envelopes are closed. Unknown top-level fields, unknown operation parameters,
missing fields, invalid IDs, duplicate IDs, unsupported protocol versions, and malformed
JSON all fail closed with structured errors. The backend never interprets request data as
PowerShell code and exposes no `configPath`, `command`, `script`, `expression`, or executable
field.

### 3.1 Implemented operations

| Operation | P3 behavior |
| --- | --- |
| `hello` | Returns backend version, `devws-editor/1`, the five supported operations, limits, and truthful capabilities. |
| `inspect` | Returns effective/canonical config metadata, source, canonical existence, physical writability, SHA-256, schema version, default set, sets/profiles, and monitor topology. |
| `read-config` | Reads the effective config bytes once, hashes those bytes, verifies `expectedSha256`, parses and validates the same bytes, and returns the complete document. |
| `project` | Resolves one set (default set when `setId` is omitted) through `Get-DevWSEffectiveLayout` and returns effective rectangles, provenance, relative/profile status, reachability, warnings, and topology metadata. |
| `shutdown` | Returns `{ "stopped": true }` and exits with code 0. |

`validate`, `preview`, `convert`, and `save` are not implemented. They return
`unsupported-operation` without executing anything. stdin EOF also exits cleanly.

### 3.2 Capability truthfulness

P3 is read-only even when the effective configuration is physically writable:

- `hello.supportedOps` contains only `hello`, `inspect`, `read-config`, `project`, and
  `shutdown`.
- `hello.limits.saveTimeoutMs` is `null` because no save operation exists.
- `hello.capabilities.saveSupported` is `false`.
- `inspect.config.writable` reports physical file writability; `inspect.capabilities.canSave`
  is always `false` in P3.

The P1 contract now states this distinction explicitly in section 4.3.1. The full-contract
example values `saveSupported: true` and `saveTimeoutMs: 30000` remain the target for a later
phase that actually implements saving.

The reader calls `ReadAllBytes` once, hashes that byte array, decodes and parses the same
array, then validates the parsed document. It does not hash one read and parse a second
read. A stale `expectedSha256` returns `external-change` without returning a document. A
change between `inspect` and `project` produces a new `project.configRevision` rather than a
fabricated stable snapshot.

Additional focused assertions cover an oversized config (`config-too-large`), invalid JSON
and invalid schema (`config-invalid`), a missing effective config (`config-unavailable`), and
a changed revision between `inspect` and `project`.

## 7. Projection parity

`project` delegates to `Get-DevWSEffectiveLayout`; the projection helper only adapts the
resolver result to the protocol model and adds warning details. It does not select profiles,
resolve anchors, clamp coordinates, or compute reachability independently.

### 7.1 Host-topology parity

The focused suite built the same fixture with the current host topology and compared every
item against `Get-DevWSEffectiveLayout`:

| Item | Source | Effective rect | Placement |
| --- | --- | --- | --- |
| `abs` | `fallback` | `0,0,800x600` | `fallback` |
| `rel` | `profile` | `200,200,600x600` | `profile` |
| `prof` | `profile` | `100,100,500x500` | `profile` |

For each item, `x`, `y`, `w`, `h`, `source`, and `placementStatus` matched the resolver
(18 field-level parity assertions). The profile matched `docked`; the sparse omission of
`abs` correctly fell back to its absolute layout; the profile entry overrode `rel`'s
relative placement.

### 7.2 Synthetic topology cases

These tests call the same projection helper with explicit synthetic topology objects. The
production protocol has no topology-injection field.

| Case | Observed result |
| --- | --- |
| Negative physical origin | Left monitor at `-1920,0,1920x1080`; relative item resolved to `x=-1920`, `w=960`; no clamping. |
| Missing relative anchor | `relativeStatus=anchor-missing`, `source=relative-fallback`, warning emitted. |
| Ambiguous relative anchor | Duplicate identity produced `relativeStatus=anchor-ambiguous` and a warning. |
| Unreachable placement | `applyGeometry=false`; warning emitted. |
| Unavailable topology | `topology.available=false`; relative item not applied. |
| Incomplete topology | `identityComplete=false`, `correlationComplete=false`; a present identity still resolved. |
| Absolute placement | Absolute layout selected as `fallback` with the saved rectangle. |
| Relative placement | Relative rect resolved from the monitor work area. |
| Matching profile | `profileMatch.status=matched` with the profile ID. |
| Profile precedence | Profile entry won over relative placement for `rel`. |
| Sparse profile | Omitted `abs` entry fell back to absolute layout. |
| Unknown set | `set-not-found` error; nothing projected. |

Negative coordinates are preserved. Missing or ambiguous anchors are represented as warnings
and statuses, never silently replaced. The backend does not use WPF, WinForms, or independent
screen measurements for geometry.

## 10. Limitations and unexecuted cases

- **Bundled-default end-to-end case is NOT EXECUTED.** `Get-DevWSCanonicalConfigPath` uses
  `[Environment]::GetFolderPath('UserProfile')`, which ignores a child-process `USERPROFILE`
  override. Isolating the case would require touching the real canonical configuration, which
  P3 forbids. The focused suite records this as an explicit environment skip rather than a
  pass. The resolver's bundled-default behavior remains covered by the existing canonical
  suite.
- **Six deferred v0.3 physical/guest qualification scenarios remain NOT QUALIFIED.** P3 did
  not qualify mixed-DPI topology, negative physical origin on real hardware, physical EDID
  identity, primary-monitor changes, or disconnect/reconnect. Synthetic topology tests are
  not physical monitor qualification.
- **No WPF/backend integration.** The P2 prototype remains an independent feasibility
  artifact. P3 does not connect it to the backend.
- **No save/validate/preview/convert.** These operations are intentionally absent and
  refused.
- **No installer or packaging change.** The approved self-contained folder direction is
  architectural only for P3.
- **No direct keyboard/UIA accessibility smoke.** That P2 limitation is unchanged.

## 12. Next-phase readiness

The read-only backend is ready to be consumed by a future editor host:

- A stable `devws-editor/1` handshake with truthful P3 capabilities.
- Revision-bound full-document reads.
- Resolver-backed projections with provenance and warnings.
- Clean shutdown/EOF and bounded transport behavior.
- No privilege, write, or live-window surface to unwind before P4.

P4 work is not authorized by this phase. Any future save/validate/preview/convert work must
extend the contract and add its own privilege, atomicity, and warning-review evidence.
