## 2. Architecture

P5 adds a lossless in-memory draft layer above the P4 read-only projection. The saved
projection remains authoritative and is never overwritten by draft geometry.

```text
DevWS.Editor.exe (Medium, asInvoker)
  ├─ saved projection (P3/P4) — remains the backend-described canonical view
  ├─ DraftDocument (System.Text.Json.Nodes)
  │    ├─ full read-config document, unknown properties preserved
  │    ├─ base SHA-256 + topology fingerprint binding
  │    └─ authorized geometry mutations only
  └─ persistent ws-editor-backend.ps1 child (Medium)
       ├─ hello / inspect / read-config / project / shutdown
       └─ validate / convert (read-only)
```

| Component | Responsibility |
| --- | --- |
| `src/editor/gui/DraftDocument.cs` | Full-document JSON-node draft, scope lookup, authorized mutations, revert/discard, mutation allowlist. |
| `src/editor/gui/RectEditMath.cs` | Pure move/resize math and resize-handle hit testing. |
| `src/editor/gui/EditorSession.cs` | Adds `inspect`, `validate`, and `convert` calls to the existing loading sequence. |
| `src/editor/gui/EditorViewModel.cs` | Draft lifecycle, geometry scope, numeric editing, drag/resize commits, validation, conflicts, revert/discard. |
| `src/editor/gui/WorkspaceCanvas.cs` | Saved outline + local draft overlay, drag/resize handles, render/text cache. |
| `src/editor/gui/MainWindow.xaml(.cs)` | Edit panel, scope/basis controls, draft badge, disabled Save, close confirmation. |
| `src/editor/editor-projection.ps1` | Structural validation adapter and authoritative `convert` adapter. |
| `src/editor/ws-editor-backend.ps1` | Advertises and implements `validate`/`convert`; still refuses `preview` and `save`. |

## 3. Draft data model

`DraftDocument` is created directly from `read-config.document`:

- the complete v3 document is parsed into `JsonObject`/`JsonArray` nodes;
- a second deep copy is retained as the baseline;
- all unknown top-level, set, item, profile-entry, and layout properties survive
  unchanged through edits and serialization;
- `BaseSha256` is the `read-config.sha256` also compared with `inspect` and `project`;
- `BaseTopologyFingerprint` is the inspect/project fingerprint;
- `SetId` is the selected workspace set;
- `IsDirty` is a structural comparison, so writing a value back to its original value
  clears the dirty state.

The draft is never reconstructed from the typed read-only projection models.

### 3.1 Authorized mutations

The public mutation surface exposes only:

- `item.layout.{x,y,w,h}` — absolute fallback;
- existing `layoutProfiles[<profileId>].layouts[<itemId>].{x,y,w,h}` — no entry creation;
- `layoutRelative.rect.{x,y,w,h}` — only with the existing anchor/basis preserved;
- coherent mode changes: `layoutMode` plus `layoutRelative` together, or
  `layoutMode: "absolute"` with `layoutRelative` removed.

A pure mutation guard (`DraftDocument.FindViolations`) compares the baseline and draft
documents by JSON path and refuses anything outside that scope. It rejects:

- commands, paths, arguments, tabs, working directories;
- item/set identity or membership, bindings, `defaultSet`;
- matchers, profile structure, profile creation/removal;
- unknown-property changes;
- geometry in another set;
- incoherent `layoutMode`/`layoutRelative` combinations.

`EditorSession.ValidateAsync` calls `EnsureMutationScope` before sending `validate`, and
the backend still performs the canonical structural validation. `preview`/`save` remain
unimplemented, so the client-side allowlist is not a substitute for a save-time check.

## 4. Editing interactions

- Item selection drives scope, editable fields, details, and the canvas overlay.
- Geometry scope selector:
  - absolute fallback (`item.layout`);
  - existing matched profile entry (`layoutProfiles[...].layouts[...]`);
  - relative placement (`layoutRelative`).
- Dragging a selected item moves its proposed rectangle; resizing uses eight visible
  handles. Both are local canvas operations only; no backend request is made during
  mouse movement.
- On mouse release, the proposed rectangle is committed to the in-memory draft. Relative
  commits call backend `convert`; absolute/profile commits write their own stored field.
- Numeric X/Y/W/H fields accept signed 32-bit integers, allow negative X/Y, and reject
  malformed input or non-positive width/height without changing the draft. Enter applies.
- Revert item restores all authorized geometry for the selected item.
- Discard all restores the full baseline document and clears previews/validation.
- The top bar shows an orange **UNSAVED DRAFT — n item(s)** badge while dirty.
- A disabled **Save (P5 unavailable)** button is shown; no functional save exists.
- The canvas draws the saved effective rectangle as a dashed outline and the proposed
  draft rectangle as a dashed amber overlay. The overlay is explicitly labeled as a
  local draft, not a backend-validated projection.
- Closing with unsaved changes opens an explicit “Discard the draft and close?” dialog.

## 5. Backend `validate`

`validate` accepts a complete draft document and calls the existing `Assert-DevWSConfig`.

- A structurally valid draft returns `ok:true` with `valid:true`, `saveEligible`, and no
  errors.
- A structurally invalid draft is still a successful response with `valid:false` and
  canonical messages. For example:

```json
{
  "code": "config-schema-invalid",
  "message": "sets[0] ('main') windows[0] ('demo') layout.w must be greater than 0 (got -5).",
  "setId": "main",
  "itemId": "demo",
  "field": "layout.w"
}
```

- Unknown properties are ignored by validation and preserved by the draft model.
- `validate` does not read topology, does not check terminal path existence, performs no
  writes, and never executes configured commands.
- `saveEligible` is `false` for an invalid draft or a non-writable resolved location; it
  is not a save authorization.

## 6. Backend `convert`

`convert` uses the existing relative-layout implementation:

- `Resolve-DevWSRelativeLayoutAnchor`;
- `Select-DevWSRelativeAnchorFromRect` when `selectAnchor:true`;
- `Test-DevWSRelativeAnchorPersistable`;
- `ConvertFrom-DevWSAbsoluteRectToRelative`;
- `ConvertTo-DevWSRelativeAbsoluteRect`;
- `Test-DevWSRectReachable`.

It supports explicit `anchor` or `selectAnchor`, `workArea`/`monitor` basis, optional
topology fingerprint checking, negative origins, six-decimal edge rounding, round-trip
information, and reachability. Missing, ambiguous, and unpersistable anchors are refused
with structured codes. The GUI stores the backend’s normalized fractions; it does not
implement independent fraction math.

Both `validate` and `convert` remain read-only. `hello.supportedOps` now advertises seven
operations (`hello`, `inspect`, `read-config`, `project`, `validate`, `convert`,
`shutdown`); `preview` and `save` remain absent and refused.

## 7. Scope and precedence evidence

The UI never silently retargets a stored field:

- selecting a profile-controlled item defaults to the existing profile entry and rewrites
  only `layoutProfiles[...].layouts[itemId]`;
- selecting a relative item defaults to `layoutRelative`; its absolute fallback is not
  changed;
- selecting an absolute item defaults to `item.layout`;
- the absolute fallback remains available for a profile/relative item as an explicit
  scope;
- mode conversion is an explicit button action and writes `layoutMode` and
  `layoutRelative` coherently. Relative-to-absolute uses the backend round-trip rectangle
  and removes `layoutRelative`; absolute-to-relative uses backend anchor selection.

A matched profile entry still takes precedence over relative placement after a mode change;
the UI explains that conversion changes the item’s stored mode/fallback, not the profile
entry.

## 8. Revision and topology drift

- The draft stores the exact base revision and topology fingerprint.
- Refresh with a clean draft reloads normally.
- Refresh with a dirty draft first calls `inspect`:
  - changed canonical hash → `external-change` conflict, draft preserved, no rebase;
  - changed topology fingerprint → `topology-changed` conflict, relative/profile commits
    blocked;
  - unchanged → saved projection refreshed while the draft is preserved.
- Every absolute edit checks the canonical revision before applying.
- Relative/profile edits additionally check the topology fingerprint; `convert` also
  receives the base fingerprint, so a drift between the check and conversion is refused.
- A conflict banner offers **Discard draft & reload**. There is no automatic merge.
- Switching sets while dirty is blocked with a visible explanation.

## 9. Performance investigation

P4 baseline (same 200-item synthetic fixture):

| Measurement | P4 |
| --- | ---: |
| First load | 8127.2 ms |
| Refresh | 4938.6 ms |
| Working set | 156.76 MB |

P5 200-item stress medians (two runs):

| Measurement | P5 |
| --- | ---: |
| First load | 8591.7 ms |
| Refresh | 4758.2 ms |
| Backend handshake | 1755.7 ms |
| Backend `project` request | 1992.3 ms |
| Project response size | 144,368 bytes |
| JSON response parse | 1.1 ms |
| C# projection model construction | 10.9 ms |
| WPF item collection update | 1.6 ms |
| Canvas render (last frame) | 14.9 ms |
| Draft document creation | 0.7 ms |
| Structural `validate` | 1603.4 ms |
| Edit commit | 1536.5 ms |
| Working set | 167.55 MB |

The load/refresh cost is dominated by the PowerShell backend: `project` alone is
~2.0 s, and the full sequence also calls topology and config inspection in separate
operations. JSON parsing, typed model construction, WPF collection replacement, and
canvas drawing together are a small single-digit-millisecond-to-tens-of-milliseconds
fraction. The 200-item `validate` is also PowerShell-bound (~1.6 s); this is a stress
observation, not a production interaction target. Working set increased by about 11 MB
versus P4 because the draft retains both the baseline and working JSON trees.

Optimizations applied without redesign:

- drag/resize never invokes a backend operation; only the release commit calls
  `inspect`/`validate` (and `convert` for relative scope);
- drag frames only update one local overlay rectangle, not the `Items` collection or the
  projection model;
- the canvas caches `FormattedText` per text/size/brush/DPI (213 cached entries in the
  200-item stress run) and reuses a frozen grid pen;
- saved rectangles are outlined independently of the draft overlay.

P4 did not record a C#/WPF split, so the P5 table is the first granular local baseline.
The cache targets repeated text construction during pan/zoom; it does not change the
backend-dominant load/refresh numbers.

A renderer redesign or backend topology caching was not justified by these measurements;
the latter would also change per-operation freshness semantics.

## 15. Limitations and unexecuted cases

- **No save, preview, semantic saved-versus-draft diff, warning acknowledgement, or
  persistence.** P5 changes are in memory only.
- Structural `validate` is not a semantic preview and does not authorize a save.
- The canvas draft overlay is a local geometric preview, not a backend `project` result.
- Profile entry creation/removal, matcher changes, and profile structure changes are
  refused; only existing profile-entry geometry is editable.
- Relative editing preserves the existing anchor/basis; anchor/basis selection is only
  offered through explicit mode conversion using backend `convert`.
- **Mixed-DPI physical behavior: NOT EXECUTED** (host has two 100% monitors).
- **Negative physical monitor origin: NOT EXECUTED** (negative item origins and synthetic
  monitor geometry are tested; a physical negative monitor origin is not).
- Physical EDID identity, primary-monitor change, disconnect/reconnect, and installed
  product integration remain **NOT QUALIFIED**.
- The six deferred v0.3 guest/hardware scenarios remain **NOT QUALIFIED**.
- Per-shape canvas automation peers are not implemented; the item list and read-only
  details remain the keyboard/UI Automation alternative.
- The 200-item stress fixture shows backend-bound ~8.6 s loads, ~4.8 s refreshes, and
  ~1.6 s structural validation; this is not a production performance claim.
- No installer, packaging, schema migration, live-window operation, or privileged
  transport is included.

## 16. Build and launch

Requires the .NET 8 SDK and Windows Desktop runtime.

```powershell
dotnet build .\src\editor\gui\DevWS.Editor.csproj -c Release
.\src\editor\gui\bin\Release\net8.0-windows\win-x64\DevWS.Editor.exe
```

Development configuration:

```powershell
.\src\editor\gui\bin\Release\net8.0-windows\win-x64\DevWS.Editor.exe `
  --dev-config "C:\path\to\workspace.json"
```

Normal mode reads the canonical configuration and shows a `DRAFT-ONLY` badge. The
development override shows an additional `DEVELOPMENT CONFIG` badge. Launch normally;
the editor refuses High integrity.
