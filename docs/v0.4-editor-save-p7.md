## 2. Architecture

```text
DevWS.Editor.exe (Medium, asInvoker)
  ├─ full-document DraftDocument + client mutation guard
  ├─ PreviewResult / explicit review token
  ├─ SaveResult + refreshed saved projection/draft
  └─ persistent ws-editor-backend.ps1 child (Medium)
       ├─ hello / inspect / read-config / project / validate / convert / preview
       ├─ save (validate → allowlist → topology → review → guarded write)
       └─ shutdown
```

The editor never writes the configuration directly. It sends the complete draft with
`confirm:true`; the backend repeats every safety check and calls
`Save-DevWSConfig -ExpectedSha256`.

## 3. Save protocol

Request:

```json
{
  "protocol": "devws-editor/1",
  "id": "s1",
  "op": "save",
  "params": {
    "draft": { "version": 3, "defaultSet": "main", "bindings": [], "sets": [] },
    "setId": "main",
    "baseSha256": "<64 lowercase hex>",
    "topologyFingerprint": "<64 hex, conditional>",
    "confirm": true,
    "reviewToken": null
  }
}
```

The `draft` above is abbreviated and non-executable; the real draft is the complete v3
document.

Success:

```json
{
  "saved": true,
  "changed": true,
  "previousSha256": "<base revision>",
  "newSha256": "<confirmed persisted revision>",
  "canonicalPath": "<effective writable configuration path>"
}
```

No-op success returns `saved:true, changed:false` with `previousSha256 == newSha256` and
does not replace the file or change its timestamp.

Capability changes:

- `hello.supportedOps` now includes `save` (nine operations).
- `hello.limits.saveTimeoutMs` is `30000`.
- `hello.capabilities.saveSupported` is `true`; `readOnly` is `false`.
- `inspect.capabilities.canSave` is `true` only for a writable effective configuration;
  bundled-default/non-writable sources report `false` and `config-not-writable`.

Refusal codes implemented in the save path: `request-invalid`, `config-invalid`,
`config-unavailable`, `config-not-writable`, `external-change`, `unsupported-mutation`,
`topology-changed`, `topology-unavailable`, `topology-incomplete`,
`warnings-not-acknowledged`, `review-stale`, `save-failed`,
`save-outcome-uncertain`, and `backend-internal`.

## 4. Server-side check order

1. Validate request structure, size, depth, `confirm:true`, and review-token shape.
2. Validate the complete draft with `Assert-DevWSConfig`.
3. Resolve the effective configuration; refuse non-writable/bundled-default sources.
4. Read the current bytes and compare SHA-256 with `baseSha256`.
5. Run the complete geometry-only mutation allowlist independently of the WPF guard.
6. Recheck topology for relative/profile/mode changes, or when a fingerprint was supplied.
7. Detect a semantic no-op and return without writing.
8. Recompute acknowledgement-required warnings and the review token.
9. Refuse missing (`warnings-not-acknowledged`) or stale (`review-stale`) review.
10. Persist through `Save-DevWSConfig -ExpectedSha256`.
11. Re-read, validate, hash, and return the confirmed result.

The allowlist is the P6 implementation: full canonical/draft comparison, structural
identity, target-set-only geometry leaves, coherent mode/relative changes, numeric
equivalence, object-key-order independence, and unchanged unknown-property preservation.
A raw protocol client cannot bypass the WPF guard.

## 5. Atomicity, mutex, and limitations

`Save-DevWSConfig` now has an optional `ExpectedSha256` and participates in
`Local\DevWS.Config.Write`.

- Bounded mutex wait: 10 seconds.
- The final expected-hash check runs while the mutex is held.
- The existing same-directory temp write → reload/validate → `File.Move(temp, target, true)`
  sequence is preserved.
- The temp file is cleaned on every failure before the move.
- Existing CLI callers that omit `ExpectedSha256` still serialize through the same mutex.
- Abandoned-mutex acquisition is treated as ownership, then the expected-hash gate runs.
- A hash mismatch throws a typed `external-change`; other pre-commit failures map to
  `save-failed`.
- Post-commit re-read failure or a contradictory revision maps to
  `save-outcome-uncertain`, never to an unchanged-file claim.

Actual guarantees:

| Property | Established |
| --- | --- |
| Atomic replacement | Same-directory temp write and replace for the single configuration file. |
| Optimistic conflict detection | Base hash compared before the write; mismatch refuses. |
| Participating-writer serialization | `Local\DevWS.Config.Write` coordinates callers of `Save-DevWSConfig` in the same user session. |
| External writers | A nonparticipating writer can still race between the final check and the move; last writer wins. |
| Cross-session/user serialization | Not promised. The mutex is `Local\`, not `Global\`. |
| Power-loss durability | Not promised; no new fsync/durability layer. |

The mutex is a coordination mechanism, not a filesystem compare-and-swap.

## 7. Refusals and uncertain outcomes

Deterministic tests prove:

- Missing `confirm`, malformed draft, invalid config, and unknown parameters refuse with no
  write.
- Stale base revision → `external-change`; bytes unchanged.
- Topology mismatch for a relative save → `topology-changed`; bytes unchanged.
- Cross-set, non-geometry, changed unknown property, and structural changes →
  `unsupported-mutation`; bytes unchanged.
- Missing warning token → `warnings-not-acknowledged`; stale token → `review-stale`; both
  leave bytes unchanged.
- Read-only/bundled-default configuration → `config-not-writable`; no canonical file is
  created.
- A read-only target replacement failure leaves the prior bytes intact and cleans the temp
  file.
- A post-commit re-read failure or unchanged observed revision is classified as
  `save-outcome-uncertain` through the deterministic confirmation helper.

GUI transport tests prove:

- Save timeout, backend exit, and malformed response are treated as uncertain.
- The fake backend's save counter is exactly `1` for each failure: no automatic retry.
- The uncertain state reports the read-only inspected revision and keeps the dirty draft.
- A backend restart does not replay a save.

The residual external-writer race is not converted into a stronger guarantee: a writer that
ignores the mutex can still change the file between the final hash check and the replace.

## 8. Warning review and topology

Save recomputes warnings from the current canonical document and topology. It reuses P6's
deterministic review keys, digest, and token binding.

- Acknowledgement-required warnings without a token refuse.
- A token from a different revision, topology fingerprint, or warning context refuses as
  stale.
- Absolute-only saves do not require topology; an optional supplied fingerprint is still
  checked when topology is available, and an unavailable topology cannot verify a supplied
  fingerprint.
- Missing/ambiguous anchors may remain warnings for an otherwise authorized save; they are
  never silently converted to absolute placement.
- A review token is freshness binding, not proof that a person read the warning. The WPF
  editor separately records the explicit **Review warnings** action.

## 9. WPF save workflow

The Save button is enabled only when:

1. a current authoritative preview exists for the exact draft;
2. no draft conflict exists;
3. the effective configuration is writable;
4. all acknowledgement-required warnings have been explicitly reviewed; and
5. no uncertain save outcome is pending.

The confirmation dialog identifies the target set and effective configuration path and
states that the file will be replaced while live windows will not be moved, focused, or
relaunched. The GUI submits `confirm:true`, the base revision, the draft topology
fingerprint, and the review token when required.

On success the editor re-loads the saved document/projection and only then clears the
dirty draft. On refusal it preserves the draft and shows the structured reason. On an
uncertain outcome it does not retry, performs a read-only inspect, reports the observed
revision, and keeps the draft until the user resolves the state.

## 14. Limitations and unqualified scenarios

- No installer, packaging, release-candidate, schema-migration, or live-layout integration.
- No automatic save retry. A save timeout/exit/malformed response remains uncertain until
  inspected.
- No hard compare-and-swap against external writers; the documented residual race remains.
- No cross-session/user serialization; `Local\` mutex only.
- No power-loss durability guarantee beyond the existing implementation.
- The 200-item save is a stress measurement, not a production latency promise.
- Mixed-DPI, physical negative monitor origin, EDID/primary/disconnect, installed-product
  integration, and the six deferred v0.3 hardware/guest scenarios remain **NOT QUALIFIED**.
- The real configuration had no save performed against it; interactive persistence used a
  disposable copy with the visible development badge.

P7 stops here. No P8 work, lifecycle integration, or additional editing capabilities were
started.
