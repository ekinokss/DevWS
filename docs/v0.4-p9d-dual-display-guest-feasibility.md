## 3. Candidate approaches and constraints

### Approach A — `mstsc.exe` with a hand-authored `.rdp` file (strongest documentary support)

Set `use multimon:i:1` and `selectedmonitors:s:<first>,<second>` where the **first** ID is the
display that should become primary in the guest session.

**Reasoning (hypothesis, not verified):** if the physically right-hand display is listed first,
it becomes primary in the guest at `(0,0)`, and the other selected display is positioned
relative to it. Because virtual-screen coordinates are anchored on the primary, the remaining
display would then be expected at a negative X.

**Constraints, each of which is a real risk:**

1. **Contiguity — corrected.** Microsoft's Win32 documentation defines a contiguous
   arrangement geometrically, not numerically: *"The monitors must form one contiguous region,
   that is, each monitor touches another monitor on at least part of one edge"*
   (`about-multiple-display-monitors`). The host's two panels share an edge, so the
   **arrangement is contiguous**. The non-consecutive monitor IDs `0` and `3` are therefore
   **not** evidence of a non-contiguous arrangement, and an earlier draft of this document was
   wrong to imply that. What remains genuinely untested is the narrower question of **RDP's
   exact acceptance behaviour** for a `selectedmonitors` list whose IDs happen to be
   non-consecutive — the property documentation does not say whether the contiguity check
   inspects geometry or the ID list.
2. **Ordering semantics.** The documentation says the first ID becomes primary; it does **not**
   say the client's left-to-right geometry is preserved, mirrored, or recomputed. A
   right-then-left listing might produce a mirrored layout, a reordered layout, or a
   single-display fallback.
3. **Monitor count in the guest — corrected.** A Hyper-V guest has one console display adapter,
   but that is **not** inherently a blocker for multiple monitors in an RDP session. Microsoft
   documents that a remote terminal is served by a **WDDM remote Indirect Display driver**, and
   that "the WDDM remote driver can expose **up to 16 monitors** to the remote session"
   (`consoles-vs-terminals`). The console adapter's displays are associated with the console
   terminal and are *not* enumerated in a remote session. So the RDP route has a documented
   mechanism for presenting multiple monitors; the untested part is whether **two selected
   client displays** actually enumerate as two separate guest monitors in this configuration,
   not whether the mechanism exists.
4. **Enhanced Session Mode is not the full mstsc surface.** Combined with the Q&A statement
   above, assuming VMConnect can carry arbitrary `selectedmonitors` settings is unsupported.

### Approach B — conventional RDP to the guest (cleanest isolation, different blocker)

Connect `mstsc` directly to the guest over the internal switch with an `.rdp` file carrying
`use multimon:i:1` and `selectedmonitors:s:…`.

- **Advantages:** uses the documented client surface that actually implements these properties;
  keeps the elevated broker, tasks and all product state inside the guest; no host display
  change at all.
- **Blockers:** the guest needs RDS enabled and inbound 3389 reachable over the internal
  switch; the host has RDP disabled (`fDenyTSConnections=1`) but that is unrelated to guest
  inbound. A disposable guest would need RDP explicitly enabled — which is a supported,
  in-guest change, but it is an additional in-guest security surface that must be removed with
  the guest.
- **Same unknowns as A:** whether two selected client displays enumerate as two guest monitors,
  and the actual resulting layout semantics.

### Approach C — add a second synthetic display adapter to the guest (bypasses RDP entirely)

Give the guest two virtual video adapters and arrange them with the same CCD method already
proven in P9-C.

- **Advantages:** removes RDP from the equation; the negative origin would be produced by the
  same in-guest mechanism P9-C already validated on real hardware; `path:` identities are
  generated **by the guest's own** PnP enumeration.
- **Blocker:** Hyper-V's console video device presents **one** display per VM. There is no
  supported Hyper-V setting that adds a second *console* display to a Windows guest. P9-BR2
  already observed a single `HyperVMonitor` (1024×768) in a Gen2 guest. **Approach C is
  therefore not expected to work for a Windows guest** and is recorded as rejected-on-evidence.
  Note the contrast with RDP: the remote terminal's indirect display driver is a *different*
  mechanism and is documented to expose up to 16 monitors (see constraint 3 under Approach A),
  so this limitation does **not** carry over to Approach A/B.

### Approach D — non-Windows/RDP-brokered or third-party virtual display driver

Rejected without investigation: introducing a third-party display driver into a qualification
guest adds an unbounded variable and is not acceptable as product evidence.

### Constraint that applies to every approach

**No approach can be validated without running a guest.** Every claim about the resulting
topology, the negative origin, and per-display `path:` identity is currently a hypothesis.
P9-C established only that the *editor and resolver* handle a negative origin correctly on real
hardware; it says nothing about whether a guest can *produce* one.

## 4. Answers to the eight required questions

| # | Question | Verdict |
| --- | --- | --- |
| 1 | Can VMConnect Enhanced Session Mode expose two distinct guest displays with a negative origin? | **Not established, and documentation points against the simple case.** VMConnect is explicitly not the full mstsc surface and documents no multi-monitor capability. **Requires physical execution to settle.** |
| 2 | Is conventional RDP a viable fallback? | **Plausible but unproven.** It is the documented surface for `use multimon`/`selectedmonitors`, and a remote terminal's indirect display driver is documented to expose up to 16 monitors, so the mechanism exists. What is untested is RDP's exact acceptance behaviour for this non-consecutive ID list and whether two selected client displays enumerate as two guest monitors. |
| 3 | Can the arrangement be achieved without modifying host display positions, scaling, primary designation or resolution? | **Yes in principle, for RDP approaches.** Approach A/B change only the *client session* geometry; the host CDS/CCD state is never written. This is the strongest argument for the RDP route over the P9-C host rearrangement. Approach C would also avoid host changes but is not expected to work. |
| 4 | Does each guest display receive a distinct, sufficiently stable `path:` identity? | **Unknown.** `Get-DevWSMonitorIdentityToken` derives `path:<DevicePathInstance>` from the guest's own PnP monitor device path. RDP-presented displays produce a **remote/virtual display device** identity, not a physical panel's EDID. Whether two RDP displays yield two *distinct* device-path instances, and whether they are stable across reconnects, is untested. This is a design risk: an RDP display may enumerate identically for both monitors. |
| 5 | Do the elevated broker and scheduled tasks work in the resulting RDP/enhanced session? | **Likely, with one caveat.** Both P9-BR2 (VMConnect/console session) and prior work used the scheduled-task path successfully inside a guest. RDP sessions are ordinary interactive sessions, so `Interactive` logon tasks should run. **Caveat:** the `DevWorkspace-ElevatedBroker` task uses a logon trigger; session type can affect whether it has already started. Needs verification in-session. |
| 6 | Can `GetWindowRect` and DWM measurements be taken from the same session as the managed window? | **Yes, expected.** Both must run in the same interactive session as the window. In a guest acceptance harness this is already the established pattern (P9-BR2 measured in session 1). Over RDP the measurement process must run inside the guest session, not on the host. |
| 7 | What temporary network, credentials, activation and installed-product dependencies are required? | Guest needs: Windows 11 Enterprise Evaluation media (hash-verified), a temporary NAT connection for activation only, a disposable local administrator, PowerShell 7, Windows Terminal (in-box), machine-wide AutoHotkey v2, and the published installer (or a candidate). For RDP: RDS enabled in-guest plus firewall scope limited to the internal switch. |
| 8 | Can all dependencies stay inside the guest and be removed afterwards? | **Yes, by construction**, exactly as P9-BR2 did: the VM, its VHDX, ISOs, staging directory, scripts and credentials are all inside deletable resources. The host privileged root, tasks, config and installation are untouched because the guest has its own. |

## 5. Feasibility verdict

**Not established.** Split by confidence:

| Claim | Confidence | Basis |
| --- | --- | --- |
| A negative-origin topology is achievable *in some RDP session* by selecting the right-hand display first | **Moderate hypothesis** | Documented "first ID becomes primary" + documented virtual-screen semantics |
| The same works over Hyper-V **VMConnect Enhanced Session Mode** | **Low** | VMConnect is explicitly not the full mstsc surface; no multi-monitor capability documented |
| A conventional RDP session to a disposable guest is a viable fallback | **Moderate** | Correct documented client, and remote terminals have an indirect display driver documented to expose up to 16 monitors; RDP's acceptance behaviour for this ID list is untested |
| Adding a second **console** display to a Windows Hyper-V guest works | **Low / rejected** | Hyper-V presents one console display per VM; P9-BR2 observed exactly one. Does not apply to RDP, which uses a different driver |
| Guest displays receive distinct stable `path:` identities | **Low** | RDP displays are virtual devices; duplication is plausible |

**Nothing here justifies marking D2 installed lifecycle as PASS, or even scheduling it as a
formality.** The negative-origin premise is credible; the identity premise is the weaker one
and is the more likely failure.

## 7. Test and evidence criteria (for a future authorised run)

A bounded run would have to demonstrate all of the following, each with its own artifact:

1. Guest session with **two** displays and a genuine **negative X** origin, captured by
   `GetSystemMetrics(SM_XVIRTUALSCREEN)` and `Screen.AllScreens`.
2. Distinct, stable `path:` identity per display, captured twice across a reconnect.
3. Relative-layout authoring through the **installed** CLI, exactly as P9-BR2 did.
4. Persistence plus a fresh-process `show-layout` resolution matching the anchor.
5. High-integrity elevated-broker launch, proven by `stage2-*` trace events and process
   parentage — not by the scheduled-helper fallback.
6. Independent `GetWindowRect` within **±1 px** of the resolved rectangle, with DWM reported
   separately.
7. Correct missing-anchor behaviour for both reachable and unreachable fallbacks.
8. Screenshots, machine-readable evidence, provenance hashes.
9. Restoration/cleanup proof plus host preservation hashes.

**Failure criteria:** origin clamped at 0; both displays enumerate with the same identity;
identity unstable across reconnect; placement on the wrong monitor; broker not used; guest
cannot present two displays at all.

## 8. Safety, cleanup and failure conditions

Prohibited in this pass and still prohibited until separately authorised: host display changes,
VM creation/start, RDP connections, network reconfiguration, privileged lifecycle operations,
production config edits, release publication.

Stop-and-report conditions for any future run:

- the guest cannot present two displays, or presents them with a clamped/non-negative origin;
- both displays resolve to the same `path:` identity;
- the broker cannot be proven to have performed the placement;
- host privileged root, tasks, config or installation change in any way;
- the host's real canonical config hash changes;
- evidence cannot be archived and verified before cleanup.

Cleanup must remove the VM, disks, ISOs, staging, scripts and credentials, and re-verify the
host config hash and protected VMs afterwards — the same standard P9-BR2 met.

## 9. Remaining uncertainties requiring supervisor approval

1. **RDP acceptance behaviour.** Does `selectedmonitors` accept this host's ID list
   (`0,3`)? The arrangement is contiguous by the Win32 geometric definition, so this is about
   the client's own validation, not about physical adjacency.
2. **Monitor enumeration.** Do two selected client displays enumerate as two separate guest
   monitors (rather than one spanning surface), given the remote terminal's indirect display
   driver supports up to 16 monitors?
3. **Identity duplication.** Will two RDP displays yield two distinct `path:` tokens?
4. **Session type vs broker.** Does the broker logon trigger behave correctly in an RDP session?
5. **Guest envelope approval**, and whether a 4 GB guest is acceptable on a host with limited
   free RAM (the P9-E resource gate requires ≥10 GiB available before provisioning).
6. **Whether to close the gap this way at all**, versus the alternative in the P9-C record:
   parameterising the privileged root, task names and broker pipe name so a fixture install can
   coexist with production on one host. That alternative has no guest-feasibility risk but is
   product work.

## 10. Judgment

**P9-D investigation: PASS** for the scope actually authorised — the candidate approaches,
their documentary support and their blockers are identified, and the eight required questions
are answered with explicit confidence levels.

**Dual-display guest feasibility: NOT ESTABLISHED.** The RDP ordering idea has real documentary
support via `selectedmonitors`, and the remote terminal's indirect display driver is documented
to expose up to 16 monitors, so the single console adapter is not a blocker. What remains
unproven is whether two selected client displays actually enumerate as two guest monitors in
this configuration, and whether they receive distinct stable `path:` identities. VMConnect is
separately documented not to be the full mstsc client.

**D2 installed lifecycle remains NOT QUALIFIED.** No PASS is claimed and none is implied.
