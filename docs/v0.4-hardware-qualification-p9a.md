### v0.3 lifecycle criteria versus v0.4 editor criteria

D1 is a **v0.3 lifecycle** qualification; the editor is not part of it (the editor never
contacts the worker/broker and never moves a window).

D2–D6 each have two distinct layers, and both must be reported separately:

| Layer | Owner | Acceptance focus |
| --- | --- | --- |
| v0.3 lifecycle | `ws launch` / `ws reset` / elevated broker | `ws show-layout` matches the frozen placement; the real managed window rectangle matches; elevated hosts receive absolute rectangles only; no automatic retiling |
| v0.4 editor | Backend `inspect`/`project`/`preview`/`convert` + WPF canvas | Projection provenance and rects match the lifecycle plan; the canvas renders the full virtual screen (including negative origins); mixed-DPI rendering is legible and never feeds GUI DPI into geometry; warnings/refusals are shown, not hidden; saving never moves a live window |

A successful editor preview does **not** establish correct live-window application, and a
successful lifecycle launch does **not** establish the editor's projection or rendering
behavior. Evidence for one layer may not be reused for the other.

Synthetic topology, synthetic negative origins, and registry EDID bytes alone do not
qualify any D2–D6 row.

Key findings:

1. **D3 is blocked on this hardware.** Both EDID records carry placeholder/absent serials,
   so DevWS correctly resolves `path:` identities. No `edid:` token can be authored or
   observed. A different physical monitor (or an owner decision) is required. Registry EDID
   data alone is not accepted as proof of physical identity.
2. **D2, D4 and D5 all require a display change.** The host is currently uniform 100% with
   no negative origin, so each scenario needs its own single-variable change and restore.
3. **Physical tests must not use the real user configuration.** The real installation is
   source-mode without the editor. Physical runs should use a disposable local Windows
   account with its own canonical config and a disposable fixture set; the real account's
   configuration and state must remain untouched.
4. **D1 is independent of the physical host.** It needs a disposable guest with a single
   virtual display; a second virtual display is not required and is not reliably available
   under Hyper-V basic sessions.

## 7. Restoration plan (for future execution only)

Captured baseline is the inventory in section 3. Before any physical session, re-capture and
store it with the evidence.

| Area | Restoration action | Automation |
| --- | --- | --- |
| Arrangement | return every monitor to its recorded position | manual in Display settings, verified by `ws monitors` |
| Primary | re-select the recorded primary | manual, verified by topology |
| Resolution | return each monitor to its recorded mode | manual, verified by topology |
| Scaling | return each monitor to 100% | manual + sign-out if required, verified by dpi/scale |
| Disconnected display | reconnect the original cable/port; if the primary vanished, wait for re-enumeration and restore primary | manual |
| Off-screen windows | bring fixture windows back with `ws reset` or the tool's window controls; never drag unknown windows | semi-automated, owner confirms |
| Editor/backend | close the editor window; if hung, terminate only the verified editor PID and its child | automated with PID ownership check |
| Configuration | restore the pre-session canonical file from a hash-verified copy | automated copy + `ws list` validation |
| Accidental real-state change | stop the session; restore the recorded real config hash; do not "repair" by rewriting | manual, owner decision |

Rules:

- One display change at a time; re-capture and confirm restoration before the next scenario.
- Any unrestorable change, any movement of a non-fixture window, or any privilege surprise
  stops the session.
- Restoration commands are **not** executed in P9-A.

For each scenario, run the lifecycle layer and the editor layer as separate evidence blocks,
and finish with a fresh topology + config comparison before moving on.
