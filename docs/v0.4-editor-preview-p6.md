## 2. Architecture

```text
DevWS.Editor.exe (Medium, asInvoker)
  ├─ saved projection from project (authoritative canonical view)
  ├─ full-document DraftDocument + client mutation guard
  ├─ PreviewResult (savedSet / draftSet / semantic diff / warnings / review)
  └─ persistent ws-editor-backend.ps1 child (Medium)
       ├─ hello / inspect / read-config / project / validate / convert / shutdown
       └─ preview (read-only, server-enforced allowlist)
```

`preview` reads the canonical snapshot once, validates the draft, acquires topology once,
then uses `Get-DevWSEffectiveLayout` for both saved and proposed sets. C# never computes
effective layout or relative geometry independently.

## 3. Server-enforced geometry-only mutation allowlist

The backend compares the complete canonical document with the complete draft independently
of the WPF guard.

Structural identity checks cover:

- schema version and `defaultSet`;
- bindings (deep equality);
- set count, order, and ids;
- item count, order, ids, and types;
- profile count, order, ids, and matcher objects;
- `layouts` key sets.

Only these leaves in the target set may differ:

```text
/sets/{setIndex}/windows/{itemIndex}/layout/{x|y|w|h}
/sets/{setIndex}/windows/{itemIndex}/layoutMode
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/monitor/{identity|instance}
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/basis
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/rect/{x|y|w|h}
/sets/{setIndex}/layoutProfiles/{profileIndex}/layouts/{itemId}/{x|y|w|h}
```

Comparison semantics:

- numbers compare by value (`0 == 0.0`);
- strings compare exactly;
- arrays compare in order;
- object keys are a set; property order is not semantic;
- absent `layoutMode` equals `layoutMode:"absolute"` (normalized for comparison);
- absent/empty `layoutProfiles` are equivalent only when no profiles exist;
- mode changes must add/remove `layoutRelative` coherently.

A direct protocol request containing a structurally valid but unauthorized `path` change
was rejected with `unsupported-mutation`, details pointing at `/sets/0/windows/0/path`.
The WPF guard was not involved.

`backend-internal`.

## 5. Semantic diff

Each entry identifies `setId`, `itemId`, stored `scope` (`fallback`, `relative`, `mode`,
`profile:<id>`), `field`, `before`, and `after`.

- An absolute fallback edit is always `scope:"fallback"`, even when a profile or relative
  placement currently takes precedence.
- A profile-entry edit is `scope:"profile:<id>"` and `field:"layouts.<itemId>"`.
- Relative edits identify `layoutRelative.rect.x/y/w/h`, `layoutRelative.basis`, or
  monitor identity/instance leaves.
- Mode conversion contributes `scope:"mode"` plus the relative-object change.
- Effective layout changes are shown only through `savedSet`/`draftSet`; the diff never
  claims an effective change for an inactive fallback.

Test evidence:

- inactive fallback change: diff `fallback`, saved/draft effective rectangles equal;
- profile entry change: diff `profile:docked`, effective rectangle changes;
- relative change: diff `relative`, draft effective follows the resolver;
- no-op: empty diff, no review token;
- numeric equivalence (`0`/`0.0`) and object key order produce no diff.

## 6. Warning review binding

Warnings have stable backend IDs, codes, messages, `requiresAcknowledgement`, and details
including set/item/profile/anchor/reason/placement context.

Acknowledgement-required codes are:

`anchor-missing`, `anchor-ambiguous`, `anchor-unpersistable`, `relative-unreachable`,
`fallback-unreachable`, `profile-unreachable`, and topology warnings when they preserve
relative/profile intent. `deferred-qualification` and informational codes are excluded.
`basis-unavailable`/`relative-invalid` are displayed but do not require acknowledgement.

Review binding:

- review keys contain only structured context (no human message);
- keys are sorted by warning id ordinal;
- canonical JSON is compact UTF-8 without BOM;
- `warningDigest` is SHA-256 of that array;
- `reviewToken` is SHA-256 of
  `devws-editor/1\n<baseSha256>\n<topologyFingerprint>\n<warningDigest>`.

Each review key is an object with this fixed property order (absent context is emitted as
`null` so the canonical bytes stay stable):

```json
{
  "id": "...",
  "code": "...",
  "setId": "...",
  "itemId": null,
  "profileId": null,
  "identity": null,
  "instance": null,
  "reason": null,
  "relativeStatus": null,
  "placementStatus": null,
  "placementReason": null
}
```

## 7. GUI preview workspace

- **Preview** action runs draft validation, then `preview`.
- Top bar reports `Preview: not run`, `Preview: 2 stored change(s)`, or
  `Preview: stale — run Preview again`.
- Canvas layers:
  - solid outline: saved effective placement;
  - teal dashed: authoritative proposed effective placement;
  - amber dashed: local unpreviewed draft;
  - handles apply to the selected stored scope.
- A legend makes the layer meanings explicit.
- Details show preview saved/proposed effective rectangles, effective-change state, active
  source, stored changes, preview warnings, and review status.
- Preview diff tab lists structured per-item changes; warnings/review tab lists warning
  consequences and the explicit **Review warnings** action.
- The action is never automatic. **Review warnings** changes the state to
  `Warnings reviewed — save remains unavailable in P6`.
- Editing, reverting, discarding, refreshing, an external revision change, a topology
  change, or a backend restart marks the preview stale and clears the review state.
- `Save (P6 unavailable)` remains disabled; `CanSave` is always false.

- `docs/assets/p6-editor-preview-diff.png` — semantic diff state.

## 8. Revision, topology, and stale-preview behavior

- Preview sends `baseSha256` from the draft and the draft's topology fingerprint.
- Canonical hash mismatch → `external-change`; supplied/required topology mismatch →
  `topology-changed`.
- Draft edits after preview mark it stale; no automatic acknowledgement survives.
- Editing after acknowledgement invalidates both preview and review.
- External revision change during refresh preserves the dirty draft and invalidates preview.
- Backend exit changes the recorded PID, so `IsPreviewCurrent` becomes false.
- Absolute-only edits can preview with topology unavailable; relative/profile edits require
  usable topology (`topology-unavailable`/`topology-incomplete`).
- No automatic rebase or draft discard occurs.

## 14. Limitations and unexecuted cases

- **No save or persistence.** Review tokens are not accepted by a save operation.
- **No acknowledgement is sent to a backend save.** The GUI records only the explicit
  review action.
- **No automatic topological reflow or live-window operation.**
- **Mixed-DPI physical behavior: NOT EXECUTED.**
- **Physical negative monitor origin: NOT EXECUTED.**
- Physical EDID, primary-monitor change, disconnect/reconnect, and installed-product
  integration: **NOT QUALIFIED**.
- The six deferred v0.3 guest/hardware scenarios remain **NOT QUALIFIED**.
- Per-shape canvas automation peers are not implemented; lists/details/diff tabs are the
  keyboard/UI Automation alternative.
- The 200-item preview is backend-bound (~4.7 s) and is a stress measurement, not a
  production performance claim.
- Real configuration had no editable relative items, so real relative preview evidence is
  synthetic; the authoritative resolver and backend were still used.
- No installer, packaging, schema migration, or update mechanism changes.
