# DevWS v0.4 Visual Editor Contract

**Status: PROPOSED — PENDING OWNER REVIEW**

This document defines the contract between a proposed normal-integrity visual workspace
editor and the existing DevWS PowerShell configuration/layout engine. It is a design
artefact only. It does not authorize or describe an implemented GUI, a new backend, a
configuration-schema change, or any change to runtime layout behaviour.

| Item | Value |
| --- | --- |
| Design baseline | `release/v0.3.0-preparation` at `fd25acac454f511d40312159e802d1fccd0fe8b1` |
| Published v0.3.0 source | `5b5d8f67191ed2f61bacbb76e6803f0e6b958f38` |
| Latest stable release | `v0.2.0` |
| Editor scope | Visual configuration authoring |
| Not in scope | A window manager, launcher, live-status monitor, daemon, or automatic reflow |

The six v0.3 deferred qualification scenarios remain **unqualified** and are carried
forward in §10. Nothing in this contract converts them into passed acceptance.

---

## 1. Purpose and scope

### 1.1 Purpose

The editor lets a user inspect the configured workspace and monitor topology, edit saved
geometry, preview the resulting effective layout, and save an explicitly approved
configuration change. It must not duplicate DevWS's configuration, monitor-identity, or
placement semantics. The existing PowerShell engine remains the semantic authority.

### 1.2 In scope

- Read-only inspection of configuration identity, workspace sets, monitor topology, and
  effective layout.
- A complete-document read bound to the exact canonical SHA-256 revision.
- Draft editing of existing items' geometry:
  - absolute fallback rectangles (`item.layout`);
  - monitor-relative intent (`layoutMode`, `layoutRelative`);
  - existing topology-profile entries (`layoutProfiles[].layouts`).
- Structural validation and semantic preview before saving.
- A server-side geometry-only mutation allowlist; the backend rejects out-of-scope changes
  even if the GUI sends them.
- One atomic canonical-configuration save with revision, topology, and warning-review
  binding.
- Explicit, visible reporting of profile, relative, fallback, missing-anchor, ambiguous,
  unreachable, and topology-change states.

### 1.3 Out of scope

- Launching, focusing, closing, moving, minimizing, or hiding live windows.
- Reading live window presence, HWNDs, UI Automation tabs, or application ownership.
- Contacting the coordinator, broker, or elevated workers.
- Adding/removing items or sets, editing commands/paths/tabs/match rules/launch rules,
  editing hotkeys, or changing the default set.
- Creating new topology profiles or re-keying profile matchers.
- Automatic reflow, monitor watching, tiling, snapping, grids, named zones, or a daemon.
- Configuration-schema changes or migration. Schema v3 remains the only runtime schema.
- Installer, packaging, release, tag, or asset changes.
- WPF implementation, GUI dependencies, or backend implementation.

### 1.4 Design principles

1. **The existing resolver is the authority.** The editor displays and edits intent; it
   does not reimplement profile/relative/fallback precedence.
2. **Normal integrity only.** The editor and backend run at the user's integrity. They do
   not load privileged code or contact privileged transports.
3. **Draft first, save once.** All edits are in memory until an explicit save. Preview is
   never a live layout operation.
4. **Fail closed.** Invalid input, stale revisions, changed topology, ambiguous identity,
   and unsupported states produce structured refusals, not guesses.
5. **Preserve what the editor does not understand.** Unknown configuration properties must
   survive a draft round trip.
6. **Do not claim qualification.** Synthetic examples and offline tests are not hardware
   acceptance.

### 2.7 Reuse versus new adapter

**Reuse directly:**

- Config location/load/validate/save.
- Monitor topology, identity, signature/fingerprint, reachability.
- Profile selection, sparse entry lookup, effective layout.
- Relative anchor resolution, absolute↔relative conversion, placement policy, anchor
  selection, anchor persistability.
- In-memory geometry mutation primitives, if needed to construct a draft.

**New, narrowly scoped adapters:**

1. `Get-DevWSConfigSha256` — SHA-256 of canonical bytes for revision tracking.
2. `Save-DevWSConfig -ExpectedSha256 <hex>` — optimistic revision check under a named mutex.
3. `Get-DevWSConfigValidationDiagnostics` — optional non-throwing validation adapter that
   returns the aggregate messages plus best-effort set/item/profile context. If the
   refactor is too invasive, the backend may return canonical messages under a generic
   `config-schema-invalid` code.
4. `Get-DevWSEditorProjection` — pure composition of config metadata, sets, topology, and
   `Get-DevWSEffectiveLayout`, plus `profileEntry` enrichment.
5. A protocol host (`ws-editor-backend.ps1`) with the allowlisted operations in §4.
6. A geometry-conversion adapter exposing `ConvertFrom-DevWSAbsoluteRectToRelative` and
   `Select-DevWSRelativeAnchorFromRect` without duplicating their math in the GUI.
7. A full-document snapshot reader (`read-config`) that hashes the same bytes it parses.
8. A semantic mutation comparator implementing §6.2.1 and a deterministic review-token
   generator implementing §4.7.1.

No new configuration schema, migration, worker protocol, or broker protocol is needed.

## 3. Process architecture

### 3.1 Component diagram

```text
┌────────────────────────────────────┐
│ DevWS.Editor (WPF, Medium)         │
│  - monitor canvas                  │
│  - set/item inspector              │
│  - draft + diff + validation       │
│  - no HWND/UIA/worker calls        │
└───────────────┬────────────────────┘
                │ UTF-8 JSON Lines over stdin/stdout
                │ one request / one response, sequential
                ▼
┌────────────────────────────────────┐
│ ws-editor-backend.ps1 (Medium)     │
│  allowlisted libraries only        │
│  inspect / project / validate      │
│  preview / convert / save          │
│  no launch / worker / broker       │
└───────────────┬────────────────────┘
                │
                ├── workspace.json (read; write only on save)
                └── DevWSMonitorNative (read-only topology + EDID)
```

The CLI and privileged path remain separate:

```text
ws.ps1 (Medium) ──► coordinator/broker ──► High workers
```

The editor does not enter that path.

### 3.2 Process lifetime

**Recommended: one long-lived backend child per editor window.**

- Started when the editor opens; exits when the editor closes or stdin closes.
- Not a daemon: it performs no work between requests, owns no timer, watches no monitors,
  and has no listening socket.
- Sequential request processing. The GUI permits one in-flight request.
- If the backend becomes unresponsive, the GUI terminates and restarts it for read-only
  operations. A save is never silently retried.

Why not a process per request:

- PowerShell startup and native-assembly loading add latency to every preview/drag commit.
- A persistent child keeps the protocol simple and interactive.
- The backend holds no authoritative state; each operation re-reads the canonical config
  and topology, so a long-lived process cannot serve stale authority.

Why not a named pipe or local HTTP server:

- A child process's stdin/stdout is already a bounded, same-user channel.
- It adds no listener, no pipe name, no network surface, and no service lifetime.
- It is easy to terminate with the GUI.

### 3.3 Startup and executable resolution

- The GUI resolves an absolute `pwsh.exe` from the installed metadata
  (`privileged.powerShellPath`) or a known Program Files PowerShell root. It does not use a
  user-writable `PATH` lookup.
- The backend script is installed at
  `%LOCALAPPDATA%\DevWS\app\editor\ws-editor-backend.ps1` and loads libraries from
  `%LOCALAPPDATA%\DevWS\app\lib`. The repository equivalent is
  `src/editor/ws-editor-backend.ps1`.
- Invocation uses `-NoLogo -NoProfile -NonInteractive -File <absolute script>`; no
  `-Command` string and no user profile.
- The GUI does not pass configuration commands or arbitrary script text as arguments.
- The backend uses the same execution-policy assumptions as `src/shim/ws.cmd`; it does not
  add `-ExecutionPolicy Bypass`.
- In installed mode the GUI sanitizes the child environment: it removes `DEVWS_CONFIG`,
  `DEVWS_STATE_ROOT`, and `DEVWS_INSTALL_ROOT` so the canonical config is used. In explicit
  development mode it may set `DEVWS_CONFIG` and must display a "development config" badge.
- If `pwsh.exe` or the backend script is missing, the editor reports a startup error and
  does not fall back to an unvalidated interpreter.

### 3.4 Transport and framing

- UTF-8, no BOM, JSON Lines: exactly one JSON object per line.
- One request line → exactly one response line. Blank lines are ignored.
- Responses are compact JSON (`ConvertTo-Json -Compress`) and contain no embedded newlines.
- `stdout` carries protocol responses only. All diagnostics, warnings, and stack traces go
  to `stderr`.
- The backend sets `$ProgressPreference = 'SilentlyContinue'` and must not emit host output
  from dot-sourced libraries.
- Maximum request line: 4 MiB. Maximum response line: 16 MiB. Maximum JSON depth: 32.
- The backend uses a bounded line reader; a line over the limit produces
  `request-too-large` and terminates the connection to avoid desynchronization.
- The GUI must not parse `stderr` as protocol data.

### 3.5 Request correlation and protocol versioning

- Every request carries `protocol: "devws-editor/1"`, a unique `id`, an allowlisted `op`,
  and an op-specific `params` object.
- The backend echoes `id` and `op` exactly.
- One in-flight request per connection. The GUI must not pipeline.
- Duplicate in-flight `id` values are a protocol error (`request-invalid`, code
  `duplicate-request-id`).
- Unknown protocol versions are refused with `protocol-version-unsupported`.
- The `hello` response advertises `supportedOps`, `limits`, and capabilities. The GUI must
  refuse to run if an operation it requires is absent.
- Response fields may be added in a compatible protocol revision; the GUI must ignore
  unknown response fields. Request fields are closed: unknown fields are rejected.
- Breaking changes require a new protocol string (`devws-editor/2`), not silent changes to
  v1 semantics.

### 3.6 Timeouts, cancellation, crashes, and restarts

| Situation | Behaviour |
| --- | --- |
| Read-only operation exceeds 10 s | GUI terminates the backend, reports `timeout`, restarts, and may retry once with a new request id. |
| `save` exceeds 30 s | GUI reports `save-outcome-uncertain`; it does **not** retry automatically. It re-runs `inspect` to compare the canonical hash. |
| User cancels a read-only operation | GUI terminates the backend and restarts; the request is reported `cancelled`. |
| User cancels a save after the request was sent | Not supported. The GUI waits for the bounded save or reports uncertainty; it never assumes failure. |
| Backend exits before a response | GUI reports `backend-exited`. Read-only operations may be retried once after restart; save is never retried. |
| Backend crashes during a save | The canonical file is either the previous file or the new file; the GUI inspects the hash. A leftover `.tmp` is overwritten by the next save. |
| Backend returns malformed JSON | GUI reports `protocol-error`, terminates, and restarts. It does not guess the result. |

The protocol has no in-band `cancel` operation because the backend is single-threaded and
PowerShell calls are not preemptible. Cancellation is process-level and is documented as
such rather than pretending to interrupt a save.

### 3.7 Resource and input limits

| Limit | Value | Enforcement |
| --- | --- | --- |
| Request line | 4 MiB | Bounded reader; `request-too-large` |
| Response line | 16 MiB | Backend cap; `response-too-large` |
| JSON depth | 32 | Parser/validator |
| In-flight requests | 1 | GUI and backend |
| Read timeout | 10 s | GUI |
| Save timeout | 30 s | GUI |
| Config document size | 4 MiB | `read-config`; `config-too-large` |
| Draft config size | 4 MiB | Request cap |
| Backend stderr | 64 KiB retained per request | GUI diagnostics only |

The backend never executes a command, script, expression, or path supplied in a protocol
message. There is no `command`, `script`, `expression`, `executable`, or `configPath` field
in any operation.

## 4. API contract

### 4.1 Envelopes

**Request**

```json
{
  "protocol": "devws-editor/1",
  "id": "1",
  "op": "inspect",
  "params": {}
}
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `protocol` | string | yes | Exactly `devws-editor/1` |
| `id` | string | yes | 1–64 chars, `[A-Za-z0-9._-]`, unique per connection |
| `op` | string | yes | One of the allowlisted operations |
| `params` | object | yes | Operation-specific; unknown fields rejected |

**Response**

```json
{
  "protocol": "devws-editor/1",
  "id": "1",
  "ok": true,
  "op": "inspect",
  "result": {},
  "warnings": [],
  "error": null
}
```

| Field | Type | Rules |
| --- | --- | --- |
| `protocol` | string | Echoes `devws-editor/1` |
| `id` | string or null | Echoes the request id when parseable |
| `ok` | boolean | `true` on success, `false` on refusal/failure |
| `op` | string or null | Echoes the request op when parseable |
| `result` | object or null | Operation result on success; `null` on error |
| `warnings` | array | Zero or more `{id, code, message, requiresAcknowledgement, details?}`; may accompany success |
| `error` | object or null | `{code, message, retryable, details?}` on failure |

**Warning object**

Every warning carries a stable, backend-generated `id`, `code`, `message`,
`requiresAcknowledgement`, and optional `details`. The `id` is deterministic for the same
semantic warning and is used only for review binding; it is not a user input.

```json
{
  "id": "anchor-missing:main:notes:edid:ACME-1234-ABC123",
  "code": "anchor-missing",
  "message": "The relative anchor is not present in the current topology.",
  "requiresAcknowledgement": true,
  "details": {
    "setId": "main",
    "itemId": "notes",
    "identity": "edid:ACME-1234-ABC123"
  }
}
```

Warnings are advisory. A warning with `requiresAcknowledgement: true` must be covered by a
review token from `preview` before `save` (§4.7, §4.9).

### 4.2 Operation summary

| Operation | Reads config | Reads topology | Mutates config | Live window side effects | Purpose |
| --- | --- | --- | --- | --- | --- |
| `hello` | no | no | no | no | Protocol/version/capability handshake |
| `inspect` | yes | yes | no | no | Config identity, sets, topology |
| `read-config` | yes | no | no | no | Complete v3 document bound to an exact canonical SHA-256 |
| `project` | yes | yes | no | no | Effective rectangles and placement metadata for a set |
| `validate` | canonical metadata only | no | no | no | Structural validation of a draft |
| `preview` | yes | yes | no | no | Saved-vs-draft effective layout and semantic diff |
| `convert` | no | yes | no | no | Absolute rect → normalized relative intent |
| `save` | yes | yes | **yes** | no | Atomic canonical write with geometry-only allowlist, revision/topology/review checks |
| `shutdown` | no | no | no | no | Clean backend exit |

### 4.3 `hello`

**Purpose:** negotiate protocol version, enumerate supported operations and limits, and
confirm backend capabilities.

**Params:** `{}` — no fields.

**Result:**

```json
{
  "backendVersion": "0.4.0-design",
  "supportedOps": [
    "hello",
    "inspect",
    "read-config",
    "project",
    "validate",
    "preview",
    "convert",
    "save",
    "shutdown"
  ],
  "limits": {
    "maxRequestBytes": 4194304,
    "maxResponseBytes": 16777216,
    "maxJsonDepth": 32,
    "maxConfigBytes": 4194304,
    "maxInflight": 1,
    "readTimeoutMs": 10000,
    "saveTimeoutMs": 30000
  },
  "capabilities": {
    "configWritable": true,
    "topologyReadable": true,
    "saveSupported": true
  }
}
```

**Errors:** `protocol-version-unsupported`, `backend-internal`.

**Side effects:** none. **Concurrency:** one request. **Cancellation:** process-level.

#### 4.3.1 P3 capability profile (implementation note)

The contract describes the eventual editor backend. The P3 implementation is read-only and
advertises only `hello`, `inspect`, `read-config`, `project`, and `shutdown` in
`hello.supportedOps`; `validate`, `preview`, `convert`, and `save` are absent and are refused
with `unsupported-operation`.

P3 therefore also reports `limits.saveTimeoutMs = null` (no save operation exists to time
out) and `capabilities.saveSupported = false`. `inspect.config.writable` continues to report
the physical writability of the effective configuration, while `inspect.capabilities.canSave`
is `false` because the P3 backend does not implement saving. A writable file must not be read
as a backend capability. The `saveTimeoutMs = 30000` value and `saveSupported = true` shown in
the examples apply only once a later phase actually implements `save`.

### 4.4 `inspect` and `read-config`

#### 4.4.1 `inspect`

**Purpose:** read configuration identity, available sets, and current monitor topology.

**Params:** `{}` — no fields. The backend uses the resolved canonical/environment config;
there is no config-path parameter.

**Success result:**

```json
{
```

#### 4.4.2 `read-config`

**Purpose:** return the complete v3 configuration document together with the exact SHA-256
revision it was parsed from. This is the only operation that supplies the full document;
`inspect` remains metadata/topology-only.

**Params:**

```json
{ "expectedSha256": "a3f1c2d4e5b60718293a4b5c6d7e8f90112233445566778899aabbccddeeff00" }
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `expectedSha256` | string | yes | 64 lowercase hex; must equal the current effective-config hash returned by `inspect` |

**Result:**

```json
{
  "sha256": "a3f1c2d4e5b60718293a4b5c6d7e8f90112233445566778899aabbccddeeff00",
  "sizeBytes": 1374,
  "document": {
    "version": 3,
    "defaultSet": "main",
    "bindings": [],
    "sets": []
  }
}
```

- The backend reads the effective config bytes **once**, computes SHA-256 from those bytes,
  and parses those same bytes. The returned hash and document are therefore one snapshot.
- If `expectedSha256` differs from the current hash, the operation fails with
  `external-change`; the GUI must re-run `inspect` and `read-config`.
- If the effective config is the bundled default, the default document is returned with its
  hash. `save` later refuses with `config-not-writable`; the GUI must show a read-only state.
- The document must fit `maxConfigBytes` (4 MiB). A larger document fails with
  `config-too-large`; the existing request/response limits are not silently raised.
- Unknown properties are preserved in the returned JSON object. The GUI must use a
  JSON-node model and must not deserialize into a lossy typed model.
- `read-config` does not read topology and does not write anything.
- After `read-config`, the GUI should call `project` and compare
  `project.configRevision` with this `sha256`. A mismatch means the config changed between
  calls; refresh before editing.

**Errors:** `config-unavailable`, `config-invalid`, `external-change`, `config-too-large`,
`backend-internal`.

**Side effects:** reads the effective config only. **Concurrency:** the expected hash
detects a change before the read; a later change is detected by `save`'s base hash.
**Cancellation:** process-level.

**Purpose:** structurally validate a proposed in-memory configuration without saving or

```json
{

    "defaultSet": "main",

    "sets": []
  }
}
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `draft` | object | yes | Complete v3 config document; not a patch |

### 4.7 `preview`

**Purpose:** compute the saved and proposed effective layouts and a semantic diff without
modifying live windows or the canonical file.

**Params:**

```json
{
  "draft": { "version": 3, "defaultSet": "main", "bindings": [], "sets": [] },
  "setId": "main",
  "baseSha256": "a3f1c2d4e5b60718293a4b5c6d7e8f90112233445566778899aabbccddeeff00",

```

| --- | --- | --- | --- |
| `draft` | object | yes | Complete v3 config |
| `setId` | string | no | Target set for the geometry-only mutation allowlist; defaults to `defaultSet` |
| `baseSha256` | string | yes | 64 lowercase hex; must match current canonical bytes |
| `baseTopologyFingerprint` | string | conditional | Required when the draft changes `layoutMode`, `layoutRelative`, or any profile/matcher scope; optional otherwise. If supplied, it must match the current topology fingerprint. |

**Result:**


The `savedSet`/`draftSet` item arrays are abbreviated in this example; their item shape is
identical to §4.5.

`diff.scope` is one of `fallback`, `relative`, `mode`, or `profile:<id>`. `field` is a
dotted path such as `layout`, `layoutMode`, `layoutRelative.monitor.identity`,
`layoutRelative.basis`, `layoutRelative.rect.x`, or `layouts.<itemId>`.
`before`/`after` are JSON values; `null` means absent.

`preview` also runs the server-side mutation allowlist (§6.2.1) and fails with
`unsupported-mutation` rather than returning a diff for an out-of-scope draft.

#### 4.7.1 Warning review binding

`preview` returns a `review` object that binds acknowledgement to the warnings actually
presented, the exact configuration revision, and the topology context.

- `warningIds` contains the stable `id` of every acknowledgement-required warning, sorted
  ordinally. Informational warnings such as `deferred-qualification` are excluded.
- `warningDigest` is the SHA-256 (64 lowercase hex) of the canonical JSON array of the
  acknowledgement-required warnings' review keys. A review key contains the warning `id`,
  `code`, `setId`, `itemId`, `profileId` (when present), monitor identity/instance (when
  present), reason, and any placement/fallback context that affects the warning. Review keys
  are sorted by `id`, serialized as compact JSON with a fixed key order, encoded as UTF-8
  without a BOM. Human message text is not part of the digest.
- `reviewToken` is the SHA-256 (64 lowercase hex) of the UTF-8 string
  `devws-editor/1\n<baseSha256>\n<topologyFingerprint>\n<warningDigest>`.
- If no acknowledgement-required warnings exist, `warningDigest` and `reviewToken` are
  `null`, and `requiresAcknowledgement` is `false`.
- `save` recomputes the warnings and token from the current canonical revision, current
  topology, and proposed draft. If any warning requires acknowledgement and `reviewToken`
  is absent, it refuses with `warnings-not-acknowledged`. If the token does not match, it
  refuses with `review-stale`. A token from a different revision, topology, warning set, or
  warning context is therefore not reusable.

**Errors:** `config-invalid`, `config-unavailable`, `set-not-found`, `unsupported-mutation`,
`external-change`, `topology-changed`, `topology-unavailable` (when a relative/profile
preview cannot be resolved), `backend-internal`.

If topology is unavailable and the draft changes only absolute fallback geometry,
`preview` succeeds with `topology.available=false` and per-item warnings; relative/profile
items are reported as unverified rather than silently treated as absolute.

**Side effects:** reads config/topology only. **Concurrency:** hard-fails if the canonical
hash or supplied topology fingerprint changed. **Cancellation:** process-level.

A preview is never a live layout operation. It does not call `SetWindowPos`, the broker, a
worker, or any lifecycle function.

### 4.9 `save`

**Purpose:** persist an explicitly approved full configuration after structural validation,
revision check, geometry-only mutation allowlist, and the topology check required by the
draft's changed scope.

**Params:**

```json
{
  "draft": { "version": 3, "defaultSet": "main", "bindings": [], "sets": [] },
  "setId": "main",
  "baseSha256": "a3f1c2d4e5b60718293a4b5c6d7e8f90112233445566778899aabbccddeeff00",
  "topologyFingerprint": "55FDA78F8E4F358F169F264CBF245A03058610CEB29DDB5AD59DD3BB172E9D6E",
  "confirm": true,
  "reviewToken": null
}
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `draft` | object | yes | Complete v3 config |
| `setId` | string | no | Target set for the geometry-only mutation allowlist; defaults to `defaultSet` |
| `baseSha256` | string | yes | Must match current canonical bytes |
| `topologyFingerprint` | string | conditional | Required when the draft changes `layoutMode`, `layoutRelative`, or any profile/matcher scope; optional for absolute-only edits. If supplied, it must match the current topology fingerprint. |
| `confirm` | boolean | yes | Must be exactly `true` |
| `reviewToken` | string or null | conditional | Required when the save is not a no-op and `preview.review.requiresAcknowledgement` is true; must equal the token recomputed from the current revision, topology, and acknowledgement-required warnings |

**Transaction:**

1. Validate `draft` with `Assert-DevWSConfig`.
2. Resolve the canonical location; refuse if `IsWritable` is false.
3. Read the canonical bytes and compute SHA-256; compare with `baseSha256`.
4. Run the server-side mutation allowlist (§6.2.1) against the target `setId`. Refuse any
   structural change, cross-set change, or non-geometry field change with
   `unsupported-mutation`.
5. If the draft changes `layoutMode`, `layoutRelative`, or any profile/matcher scope, read
   topology and require `topologyFingerprint` to match. For absolute-only edits, topology is
   optional; if a fingerprint is supplied, it must still match.
6. If the draft is semantically identical to the canonical config, return
   `saved:true, changed:false` without replacing the file. No review token is required for a
   no-op save.
7. Compute the acknowledgement-required warnings and the review token. If any warning
   requires acknowledgement and `reviewToken` is absent, refuse with
   `warnings-not-acknowledged`. If the token does not match the recomputed token, refuse
   with `review-stale`.
8. Call `Save-DevWSConfig -ExpectedSha256 <baseSha256>`.
9. Re-read the canonical file, validate it, compute the new SHA-256, and return it.

The backend determines whether topology is required by comparing the draft to the canonical
config at `baseSha256`; formatting-only differences do not count as scope changes.

**Success result:**

```json
{
  "saved": true,
  "changed": true,
  "previousSha256": "a3f1c2d4e5b60718293a4b5c6d7e8f90112233445566778899aabbccddeeff00",
  "newSha256": "b4e2d3c5f6a718293a4b5c6d7e8f90112233445566778899aabbccddeeff0011",
  "canonicalPath": "C:\\Users\\devws\\.config\\devws\\workspace.json"
}
```

**Errors:** `config-invalid`, `config-unavailable`, `config-not-writable`,
`unsupported-mutation`, `external-change`, `topology-changed`,
`topology-unavailable`/`topology-incomplete` (when the changed scope requires a usable
topology), `warnings-not-acknowledged`, `review-stale`, `save-failed`,
`save-outcome-uncertain`, `backend-internal`.

**Side effects:** writes the canonical config only. It never invokes `ws launch`, `ws
focus`, `ws reset*`, the coordinator, the broker, a worker, or a scheduled task.
**Concurrency:** revision check + named mutex; see §6.5. **Cancellation:** not supported
after the request is accepted; see §3.6.

### 4.10 `shutdown`

**Purpose:** cleanly stop the backend.

matching `reviewToken` when the warning is acknowledgement-required. The GUI must not
silently convert the item to absolute mode.

### 4.12 Warnings versus hard failures

- **Hard failure:** the operation cannot produce a trustworthy result or must not write.
- **Warning:** the operation produced a result, but the user must see a limitation,
  fallback, missing anchor, ambiguity, or deferred qualification.
- A warning never changes the stored mode, anchor, basis, or scope.
- A preview warning is not a save approval. `save` recomputes warnings and the review
  token; a token only covers the warnings returned by the matching preview.
- A deferred qualification warning (`deferred-qualification`) is informational; it does not
  claim the scenario passed.

### 4.13 Compatibility

- Protocol v1 is closed for requests and additive for responses.
- The GUI must ignore unknown response fields and must not depend on JSON property order.
- `hello.supportedOps` is authoritative; the GUI must not call an operation that is absent.
- Config schema v3 is unchanged. A v2 config produces `config-invalid` with the existing
  installer-migration message; the editor does not migrate it.
- A future schema v4 requires a new protocol/capability and a separate migration design.
- The backend may be newer or older than the GUI; both must negotiate via `hello`.
- The editor must not write a config it does not understand. Unknown item/top-level
  properties are preserved; unknown schema versions are refused.

## 5. Geometry and unit rules

### 5.1 Coordinate spaces

| Space | Definition | Authoritative for storage? | Used by |
| --- | --- | --- | --- |
| Windows physical desktop pixels | Raw pixels reported by the display driver | No | OS/driver only; not exposed as a stable DevWS contract |
| DevWS virtual-screen coordinates | Coordinates observed by the DPI-unaware PowerShell backend; monitor rectangles, work areas, stored layouts | **Yes** | All stored and effective geometry |
| WPF device-independent pixels (DIPs) | GUI layout units after WPF scaling | No | Rendering and pointer interaction only |
| Absolute stored geometry | `item.layout` and profile entries, integer `x/y/w/h` | **Yes** | Fallback and profile layers |
| Normalized relative geometry | `layoutRelative.rect` fractions of the selected basis | **Yes** | Relative intent |
| Effective rectangle | Result selected by `Get-DevWSEffectiveLayout` | **Yes** | Preview and lifecycle placement |

DevWS does not change process DPI awareness. The existing design record measured
PowerShell 7.6.7 as DPI-unaware; the current host has not been re-measured. The contract
therefore treats the backend's virtual-screen coordinates as authoritative and never
derives geometry from the GUI's DPI.

### 5.2 Canvas transform

The GUI canvas is a zoomable diagram in DevWS virtual-screen coordinates:

```text
canvasPoint = (backendPoint - virtualScreenOrigin) * zoom + pan
backendPoint = (canvasPoint - pan) / zoom + virtualScreenOrigin
```

- `virtualScreenOrigin` is `topology.virtualScreenRect.{x,y}`; negative origins remain
  negative and are handled by subtraction, not clamping.
- `zoom` is a single uniform scalar for the whole canvas. There is no per-monitor scale.
- `pan` is a single 2D offset.
- The GUI must not call `System.Windows.Forms.Screen`, `GetSystemMetrics`,
  `GetWindowRect`, or `GetDpiForMonitor` for geometry. It uses `topology.monitors`.
- `scalePercent` and `DpiEffective` are diagnostic labels only. They are not used in
  conversion or rounding.
- Mixed-DPI rendering is a P2 feasibility question. The geometry contract is independent
  of it: all edits are converted through the backend's virtual-screen coordinates.

### 5.3 Absolute geometry

`item.layout` is `{x, y, w, h}` with integer `x/y`, positive integer `w/h`. Negative `x/y`
are valid. It is the universal fallback and is mandatory for every item.

Profile entries under `layoutProfiles[].layouts[itemId]` use the same absolute rectangle
rules and are sparse. A matched profile entry overrides relative and fallback geometry for
that item.

### 5.4 Normalized relative geometry

`layoutRelative` is:

```json
{
  "monitor": { "identity": "edid:ACME-1234-ABC123", "instance": "DELA1B2/5" },
  "basis": "workArea",
  "rect": { "x": 0.0, "y": 0.0, "w": 0.5, "h": 1.0 }
}
```

- `identity` is a durable `edid:` or `path:` token. Ordinals are invalid.
- `instance` is optional; it must be omitted for `path:` identities.
- `basis` is exactly `workArea` or `monitor`.
- `rect` fields are finite numbers; `w/h` > 0; `x/y` may be negative or greater than 1.
- Capture rounds fractions to six decimal places. Explicit authoring stores the supplied
  finite values.
- `layoutRelative` is accepted only when `layoutMode` is `relative`.

Conversion rules:

- Absolute → relative: `ConvertFrom-DevWSAbsoluteRectToRelative` computes edge fractions,
  rounds each edge to six decimals with `MidpointRounding.AwayFromZero`, derives width and
  height from rounded edges, and enforces a minimum positive fraction.
- Relative → absolute: `ConvertTo-DevWSRelativeAbsoluteRect` rounds left/top/right/bottom
  edges first, derives width/height, and enforces at least 1×1 pixel.
- The GUI must call `convert` for absolute → relative authoring. It must not duplicate the
  fraction math for saved values.
- During a drag, the GUI may show an absolute preview rectangle using the canvas transform.
  On commit, it sends the absolute rect to `convert` and uses the returned normalized
  values. This keeps the canonical math in one place.

### 5.5 Effective-layout precedence

Per item, the authority is:

1. **Matched exact profile entry** — if the current topology matches a profile and the
   profile has a sparse entry for the item.
2. **Relative target** — if the item is `layoutMode: relative` and no profile entry exists.
3. **Absolute fallback** — otherwise.

A sparse matched profile omits items; omitted items fall back to their relative or absolute
layer. Profile order never resolves a conflict. A matched profile entry that is unreachable
on the current desktop causes a lifecycle refusal for profile-aware sets; an unreachable
relative target falls back only if the absolute fallback is reachable; an unreachable
fallback is skipped with a warning. `Get-DevWSEffectiveLayout` is the authority for these
decisions.

### 5.6 Negative origins and multi-monitor

- Negative monitor origins are preserved in `monitorRect`, `workRect`, `virtualScreenRect`,
  stored layouts, and normalized fractions.
- The canvas maps the entire virtual-screen rectangle; it does not clip at zero.
- Monitor order is never identity. `identity`/`instance` are durable; ordinals, source ids,
  target ids, LUIDs, friendly names, resolution, and the primary bit are not durable.
- A primary-monitor change must not remap an identity-anchored item. It may change which
  monitor is primary, but the anchor still selects by identity.
- Multi-monitor selection and negative origins remain a deferred qualification scenario
  (§10, D2); synthetic math tests do not qualify real hardware.

### 5.7 DPI and scaling

- The backend's virtual-screen coordinates are the storage contract.
- The GUI's DPI awareness affects text/control rendering, not geometry math.
- A scaling change that changes the virtualized monitor/work rectangle changes the resolved
  relative rectangle; a scaling change that does not change the virtualized rectangle does
  not.
- Physical-pixel exactness is not promised. Windows may apply DPI virtualization when a
  window crosses monitors with different scaling; DevWS already lives with this for
  absolute layouts.
- Mixed-DPI configurations remain a deferred qualification scenario (§10, D4). P2 must
  measure the GUI canvas transform on a mixed-DPI host; this contract does not claim it
  passed.

### 5.8 Missing, ambiguous, and unreachable states

| State | Projection/reporting | Save behaviour |
| --- | --- | --- |
| Topology unavailable | `topology.available=false`; relative items report `relative-unavailable`; profile-aware sets report refusal | Absolute-only edits may save; relative/profile changes fail `topology-unavailable`; preview warns |
| Topology incomplete | `identityComplete=false`/`correlationComplete=false`; profile matching ineligible; no canonical fingerprint | Absolute-only edits may save; relative/profile changes fail `topology-incomplete`; preview warns |
| Topology ambiguous | `identityAmbiguous=true`; duplicate identity at same rectangle; fingerprint may still exist | Relative/profile changes may save with a matching fingerprint and acknowledgement; profile-aware lifecycle refuses |
| Anchor missing | `relativeStatus=anchor-missing`, `relativeReason=identity-not-found`; fallback used only if reachable | Save may persist relative intent; warning; acknowledgement required |
| Anchor ambiguous | `relativeStatus=anchor-ambiguous`, `relativeReason=duplicate-identity` | Save may persist; warning; acknowledgement required; GUI must show candidate monitors |
| Anchor unpersistable | `anchor-unpersistable`; no durable identity | `convert` refuses; GUI must select another monitor or absolute mode |
| Relative target unreachable | `relative-unreachable`; fallback if reachable; otherwise skip | Save may persist; warning; acknowledgement required |
| Fallback unreachable | `fallback-unreachable`; item skipped | Save may persist; warning; acknowledgement required |
| Profile entry unreachable | `profile-unreachable`; profile-aware lifecycle refuses | Save may persist; warning; acknowledgement required |
| Matched profile with sparse omission | Item falls back to relative/absolute; `profileOverridesRelative=false` | No special warning; preview shows source |

The GUI must display the exact `relativeStatus`, `relativeReason`, `relativeMessage`,
`placementStatus`, and `placementReason`; it must not replace them with a generic
"unavailable" label.

### 5.9 Topology changes between operations

- `inspect` returns `topology.fingerprint`.
- `project`/`preview` return the fingerprint used for their computation.
- `save` requires the same fingerprint when the draft changes `layoutMode`,
  `layoutRelative`, or any profile/matcher scope. A mismatch is a hard `topology-changed`
  refusal.
- Absolute-only edits do not require topology. If the GUI supplies a fingerprint, a
  mismatch still refuses; if it omits the fingerprint, the save may proceed, but the GUI
  must re-run `preview` before presenting a refreshed visual context.
- No automatic retile, watcher, or reflow occurs between operations.

### 5.10 Provenance preservation

Each projected item carries:

- `layoutMode` (`absolute` or `relative`);
- `source` (`profile`, `relative`, `relative-fallback`, `relative-unavailable`,
  `fallback`);
- `profileId` and `profileEntry`;
- `profileOverridesRelative`;
- `relativeLayout` and `relativeRect`;
- `fallbackRect`;
- `placementStatus`/`placementReason`;
- `applyGeometry`.

The GUI must show these as explicit badges and must not change the stored mode, anchor,
basis, or profile scope unless the user performs an explicit mode/scope action. A plain
absolute edit of a relative item is refused by the existing rules; the editor must not
silently convert it.

## 6. Draft and persistence contract

### 6.1 Draft creation

1. `inspect` returns the canonical metadata, hash, sets, and topology.
2. `read-config` is called with `expectedSha256` equal to `inspect.config.sha256`; it returns
   the complete v3 `document` and the exact hash it was parsed from.
3. `project` returns the effective layout for the selected set.
4. The GUI deep-copies `read-config.document` into an in-memory draft, preserving every
   unknown property.
5. The GUI stores `read-config.sha256` as `baseSha256` and the topology fingerprint from
   `inspect`/`project` as `baseTopologyFingerprint`, alongside the draft, not inside the
   configuration document.

The GUI must compare `read-config.sha256`, `project.configRevision`, and
`inspect.config.sha256`, plus the topology fingerprints from `inspect` and `project`. A
mismatch means the configuration or topology changed between calls; the editor must refresh
before allowing edits or saving.

The draft is a **complete v3 configuration document**, not a JSON Patch and not a partial
item model. This lets `Assert-DevWSConfig` remain the single validator and avoids merge
semantics.

### 6.2 Modification representation

The GUI edits only explicit JSON paths:

- `sets[<setIndex>].windows[<itemIndex>].layout.{x,y,w,h}`
- `sets[<setIndex>].windows[<itemIndex>].layoutMode`
- `sets[<setIndex>].windows[<itemIndex>].layoutRelative.monitor.identity`
- `sets[<setIndex>].windows[<itemIndex>].layoutRelative.monitor.instance`
- `sets[<setIndex>].windows[<itemIndex>].layoutRelative.basis`
- `sets[<setIndex>].windows[<itemIndex>].layoutRelative.rect.{x,y,w,h}`
- `sets[<setIndex>].layoutProfiles[<profileIndex>].layouts.<itemId>.{x,y,w,h}`

The GUI must not reconstruct the document from a lossy typed model. It should use a
JSON-node model (`JsonObject`/`JsonArray` or equivalent) and preserve unknown properties,
property order where practical, and all non-edited values.

#### 6.2.1 Server-side mutation allowlist

The backend must not rely on the GUI to restrict edits. `preview` and `save` perform a
semantic comparison of the complete canonical configuration against the complete draft and
refuse any mutation outside the v0.4 geometry-authoring scope. The target set is `setId`
(omitted means `defaultSet`); only that set's geometry may change.

**Comparison algorithm:**

1. Parse both documents as JSON DOMs, preserving every property.
2. Verify structural identity:
   - same `version` and `defaultSet`;
   - same `bindings` (deep equality);
   - same set count, order, and ids;
   - same item count, order, ids, and types within every set;
   - same profile count, order, ids, and `match` objects within every set;
   - same `layouts` key set within every profile.
3. Walk every leaf in both documents and collect differences with a JSON Pointer-style
   path. Compare numbers by value (`0` equals `0.0`), strings exactly, arrays in order, and
   object keys as a set (object key order is not semantic).
4. Classify each difference against the allowlist below. Any difference outside the
   allowlist, any structural difference, and any change outside the target set is refused
   with `unsupported-mutation`.
5. Treat absent `layoutMode` and `layoutMode: "absolute"` as semantically equivalent.
   Treat absent `layoutProfiles` and an empty `layoutProfiles` array as equivalent only when
   both express no profiles; any non-empty profile structure must be preserved exactly.

**Allowed leaf paths (target set only):**

```text
/sets/{setIndex}/windows/{itemIndex}/layout/x
/sets/{setIndex}/windows/{itemIndex}/layout/y
/sets/{setIndex}/windows/{itemIndex}/layout/w
/sets/{setIndex}/windows/{itemIndex}/layout/h
/sets/{setIndex}/windows/{itemIndex}/layoutMode
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/monitor/identity
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/monitor/instance
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/basis
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/rect/x
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/rect/y
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/rect/w
/sets/{setIndex}/windows/{itemIndex}/layoutRelative/rect/h
/sets/{setIndex}/layoutProfiles/{profileIndex}/layouts/{itemId}/x
/sets/{setIndex}/layoutProfiles/{profileIndex}/layouts/{itemId}/y
/sets/{setIndex}/layoutProfiles/{profileIndex}/layouts/{itemId}/w
/sets/{setIndex}/layoutProfiles/{profileIndex}/layouts/{itemId}/h
```

`{setIndex}`, `{itemIndex}`, and `{profileIndex}` are stable because step 2 requires the
same order and identities. `{itemId}` must already exist as a key in that profile's
`layouts`; adding or removing a profile entry is a structural change and is refused.

**Mode-conversion rules:**

- `absolute` (or absent) → `relative` requires a valid `layoutRelative`; the mode and
  relative object must change together.
- `relative` → `absolute` requires `layoutRelative` to be removed and `layoutMode` to be
  `"absolute"` (or absent).
- Adding or removing `layoutRelative` without a corresponding mode change is refused.
- `item.layout` may change independently as the absolute fallback, including for a relative
  item. The GUI must show that relative placement takes precedence when the anchor resolves.
- `layoutMode` values other than `absolute`/`relative` fail schema validation.

**Explicitly rejected changes:**

- commands, startup arguments, tabs, paths, per-tab paths, working directories;
- set ids, set order, set membership, item ids, item order, item types, item membership;
- `bindings`, hotkeys, `defaultSet`;
- `match`, `launch`, `instanceMode`, `enabled`;
- profile ids, profile order, profile count, `match` objects, matcher tokens;
- adding/removing profile entries or `layouts` keys;
- any change to an unknown property (unchanged unknown properties are preserved);
- any geometry change in a set other than the target `setId`.

**Refusal:**

```json
{
  "code": "unsupported-mutation",
  "message": "The draft changes a field that the v0.4 editor is not authorized to modify.",
  "retryable": false,
  "details": {
    "path": "/sets/0/windows/0/path",
    "reason": "field-not-allowed",
    "targetSetId": "main",
    "allowedScopes": ["geometry", "relative-geometry", "existing-profile-entry-geometry"]
  }
}
```

`preview` runs the same allowlist and fails with `unsupported-mutation` rather than showing
a preview for an out-of-scope draft. `validate` remains structural only; a draft can be
structurally valid and still be refused by `preview`/`save`.

### 6.3 Validation

- `validate` is called after a debounce or before preview; it is not a save.
- `validate` checks the complete draft with `Assert-DevWSConfig`.
- `validate` does not check terminal path existence.
- `preview` additionally runs the geometry-only mutation allowlist, resolves topology, and
  computes the effective layout and review token.
- `save` re-validates the draft, re-runs the mutation allowlist, re-checks the revision,
  re-checks topology, re-checks the review token, and re-checks writability. Client-side
  validation is never trusted as the only gate.

### 6.4 Preview comparison

`preview` returns:

- `savedSet`: effective layout of the canonical config at the current hash.
- `draftSet`: effective layout of the draft.
- `diff`: semantic changes at the configuration-field level.
- `warnings`: topology/anchor/profile warnings.
- `review`: revision/topology-bound warning acknowledgement token (§4.7.1).

The GUI displays saved rectangles (solid) and draft rectangles (dashed), plus a per-item
source/provenance panel. It must not imply that the dashed rectangle has been applied to a
live window.

### 6.5 Revision and atomic save

**Revision:** SHA-256 of the canonical file bytes, lowercase hex. `inspect` returns it.

**Adapter:**

```text
Get-DevWSConfigSha256(path) -> 64-char lowercase hex
Save-DevWSConfig -Config <object> -Location <location> -ExpectedSha256 <hex>
```

`Save-DevWSConfig` gains an optional `ExpectedSha256` parameter:

1. Acquire `Local\DevWS.Config.Write` with a bounded wait.
2. If `ExpectedSha256` is supplied, read the current canonical bytes, compute SHA-256, and
   compare. A mismatch throws a typed conflict (`external-change`).
3. Reuse the existing temp-write → reload/validate → `File.Move(temp, target, true)`
   sequence.
4. Release the mutex.

Existing callers that omit `ExpectedSha256` keep their current behaviour but still
serialize through the same mutex.

**Concurrency guarantees and non-guarantees:**

| Property | What the implementation establishes | What it does **not** establish |
| --- | --- | --- |
| Atomic file replacement | A same-directory temp file is written, reloaded, validated, and committed with `File.Move(temp, target, true)`. A failure before the move leaves the previous canonical file intact. | A transaction across multiple files, an fsync/durable-write guarantee, or recovery from power loss beyond the existing product behaviour. |
| Optimistic revision check | `baseSha256` is compared with the canonical bytes before the write. A mismatch refuses with `external-change`. | A hard compare-and-swap. A writer can change the file after the comparison and before the replace. |
| Mutex coordination | `Local\DevWS.Config.Write` serializes participating DevWS writers in the same user session that call `Save-DevWSConfig`. | Cross-session or cross-user serialization. A `Global\` mutex is not used. |
| External writers | The editor detects a stale revision at its next `inspect`, `read-config`, `preview`, or `save`. | Any coordination with editors, scripts, or other tools that do not honor the mutex. The last writer wins. |
| Read snapshot | `inspect` and `read-config` read without holding the mutex; `read-config` hashes the same bytes it parses. | A stable snapshot across multiple calls. A change between calls is detected by hash comparison. |

The contract does not claim cross-process or cross-session serializability. The mutex is a
coordination mechanism for participating DevWS writers, not a filesystem lock. The
optimistic revision check is a detection mechanism, not a guarantee that no external write
can occur between check and replace.

**Atomicity:** the temp file is in the same directory as the canonical file; `File.Move`
with overwrite is the commit point. A failure before the move leaves the previous file
intact. There is no new persistence format or second config file.

**Durability:** the existing implementation does not fsync. Power-loss durability beyond
the current product behaviour is not promised.

### 6.6 Save failure and confirmation

| Failure point | Result |
| --- | --- |
| Draft invalid | `config-invalid`; nothing written |
| Draft exceeds 4 MiB | `config-too-large`; nothing written |
| Out-of-scope mutation | `unsupported-mutation`; nothing written |
| Revision mismatch | `external-change`; nothing written |
| Topology mismatch (supplied or required) | `topology-changed`; nothing written |
| Topology unavailable/incomplete for a relative/profile change | `topology-unavailable`/`topology-incomplete`; nothing written |
| Acknowledgement-required warning without a token | `warnings-not-acknowledged`; nothing written |
| Review token no longer matches | `review-stale`; nothing written |
| Location not writable | `config-not-writable`; nothing written |
| Temp write/validation fails | `save-failed`; canonical unchanged; temp cleaned by existing `finally` |
| `File.Move` fails | `save-failed`; canonical unchanged unless the OS reports success then throws (unexpected) |
| Move succeeds, re-read fails | `save-outcome-uncertain`; GUI must inspect the hash |
| Response lost | GUI reports `save-outcome-uncertain`; must inspect, never auto-retry |

On success, the backend re-reads the canonical file, validates it, and returns
`previousSha256`/`newSha256`. The GUI updates `baseSha256` only after `saved:true` and a
matching `newSha256`.

### 6.7 Missing configuration

- If the canonical file is absent but the bundled default exists, `inspect` succeeds with
  `source: "default"`, `canonicalExists: false`, `writable: false`, and
  `capabilities.canSave: false`. `read-config` returns the default document and its hash;
  `save` refuses with `config-not-writable`.
- If neither canonical nor bundled config exists, `inspect` returns `config-unavailable`.
- The editor does not create a canonical config, run the installer, or migrate a v2 file.
  The installer remains the only component that creates/migrates the canonical config.

### 6.8 No-op saves

If the draft is semantically identical to the canonical config, `save` returns
`saved:true, changed:false` and does not replace the file. No review token is required for a
no-op save. This avoids timestamp churn and makes repeated saves predictable.

### 6.9 No lifecycle side effects

`save` must not call `ws launch`, `ws focus`, `ws reset*`, the coordinator, the broker, a
worker, a scheduled task, or any window operation. A configuration save is not a live
layout operation. The GUI may offer a separate, explicitly authorized launch action in a
future design; it is not part of v0.4 P1.

## 7. Privilege and security boundaries

### 7.1 Integrity model

| Component | Integrity | Reads | Writes | Contacts privileged transport |

- any other library that can launch, focus, close, move, capture, or contact a host

A P3 test must parse the backend's dot-source list and assert exact equality with the

### 7.3 Protocol allowlist

- No `command`, `script`, `expression`, `executable`, `arguments`, or `configPath` fields.
- No arbitrary operation names; unknown `op` → `unsupported-operation`.
- Unknown request fields → `request-invalid`.
- No `Invoke-Expression`, `Add-Type` from request data, or dynamic script construction.
- The only path the backend resolves is the canonical config location from
  `Resolve-DevWSConfigLocation`.
- Drafts are data, not code. Config commands are never executed by the editor.
- The backend never reads a draft path from the request; drafts travel inline.

### 7.4 Environment and executable resolution

- The GUI resolves `pwsh.exe` absolutely; no `PATH` lookup.
- Installed mode removes `DEVWS_CONFIG`, `DEVWS_STATE_ROOT`, and `DEVWS_INSTALL_ROOT` from
  the child environment so the canonical config is used.
- Development mode may set `DEVWS_CONFIG` explicitly and must show a development badge.
- The backend runs with `-NoProfile -NonInteractive`; user profile code is not loaded.
- The backend uses the same execution-policy assumptions as the installed `ws.cmd`.

### 7.5 Logging and error hygiene

- Protocol responses may include canonical config paths and item ids.
- Draft contents are not logged to `stderr`.
- Error messages preserve canonical validation text but must not include environment
  secrets or unrelated user data.
- `stderr` is bounded and diagnostic only; the GUI never treats it as protocol data.

## 8. Failure semantics

### 8.1 Hard failures that block saving

- `config-invalid`: draft fails schema validation.
- `config-unavailable`: no canonical/bundled config.
- `config-not-writable`: bundled default or read-only location.
- `config-too-large`: effective config or draft exceeds 4 MiB.
- `unsupported-mutation`: draft changes a field outside the geometry-only allowlist.
- `external-change`: canonical hash differs from the base revision.
- `topology-changed`: a supplied or required topology fingerprint differs.
- `topology-unavailable`/`topology-incomplete`: the changed scope requires a usable
  topology and none can be acquired.
- `warnings-not-acknowledged`: acknowledgement-required warning has no review token.
- `review-stale`: the review token no longer matches the revision, topology, or warnings.
- `save-failed`: write failed before the commit point.
- `save-outcome-uncertain`: write may have succeeded; inspect before any retry.
- `protocol-version-unsupported`, `request-invalid`, `request-too-large`,
  `unsupported-operation`: the request cannot be trusted.

### 8.2 Warnings that do not block saving by themselves

- `anchor-missing`
- `anchor-ambiguous`
- `anchor-unpersistable`
- `basis-unavailable`
- `relative-unreachable`
- `fallback-unreachable`
- `profile-unreachable`
- `topology-unavailable`/`topology-incomplete`/`topology-ambiguous` when the operation can
  still produce a structural result
- `deferred-qualification`

The GUI must display the warning, explain the consequence, and require the matching
`reviewToken` for save when `requiresAcknowledgement` is true. The acknowledgement-required
warnings are `anchor-missing`, `anchor-ambiguous`, `anchor-unpersistable`,
`relative-unreachable`, `fallback-unreachable`, `profile-unreachable`, and
`topology-unavailable`/`topology-incomplete`/`topology-ambiguous` when the draft preserves
relative/profile intent. `deferred-qualification` is informational and does not require
acknowledgement. The GUI must not convert the item to absolute mode or change the
anchor/basis silently.

### 8.3 Preview is not launch

A preview may report "this is what launch would apply," but it must never apply it. The
response field is `draftSet`/`savedSet`, not "applied." The GUI must label the preview as a
configuration preview, not a live layout operation.

### 8.4 Ambiguity and missing monitors

The editor must show:

- the exact identity token and instance;
- the candidate monitors for an ambiguous anchor;
- the fallback rectangle and whether it is reachable;
- the skip reason when neither target is usable;
- the profile refusal reason for profile-aware sets.

It must not select a "nearest" monitor or remap by ordinal.

## 9. Compatibility requirements

- Configuration schema remains v3. No migration, no new fields, no field removal.
- The editor reads and writes the same canonical file as the CLI.
- Existing CLI commands continue to work; the editor is additive.
- Unknown item/top-level properties survive a full-document round trip.
- Existing profile matchers and relative anchors remain valid.
- The editor does not change `defaultSet`, bindings, commands, paths, tabs, match rules, or
  launch rules in the v0.4 MVP.
- A v2 config is refused with the existing installer-migration message; the editor never
  migrates it.
- A future schema v4 requires a new protocol/capability and separate acceptance.
- Protocol v1 request fields are closed; response fields are additive.
- The GUI must tolerate a newer backend that adds response fields, and a backend must
  reject unknown request fields rather than guessing.

## 10. Acceptance matrix

Legend:

- **Offline**: deterministic, no real monitor or installed product required; may use
  synthetic topology objects or a temporary config.
- **Windows host**: requires a real Windows session, real monitor topology, or fixture
  windows, but not a disposable guest.
- **Installed VM**: requires the installed product at normal integrity.
- **Hardware/guest**: requires real monitor arrangements, EDID, DPI changes, or a
  disposable guest. These are **not** qualified by this contract.

## 12. Dependencies and P2 entry criteria

### 12.1 P1 completion criteria

- This contract is reviewed and explicitly accepted by the owner.
- Every operation has defined request/response/failure semantics.
- A complete-document read is bound to an exact canonical revision.
- The server-side geometry-only mutation allowlist is accepted.
- Warning acknowledgement is bound to the reviewed revision/topology/warnings.
- Concurrency guarantees and residual races are stated without overclaiming.
- Geometry and persistence rules are source-grounded.
- Security boundaries and module allowlist are accepted.
- The six deferred scenarios remain explicitly unqualified.
- No production source, packaging, installer, schema, tag, or release change.

### 12.2 P2 entry criteria

P2 (WPF feasibility, mixed-DPI, startup, payload size) may begin only after P1 acceptance
and must answer:

1. Measured WPF publish size, compressed setup-size delta, startup time, and working set.
2. Canvas transform correctness on a mixed-DPI host (backend virtual coordinates vs WPF
   DIPs), with negative origins.
3. Keyboard/UIA accessibility smoke for the canvas and inspector.
4. Whether a prebuilt GUI binary can be embedded in the setup payload with acceptable
   provenance and verification.
5. Whether WPF remains preferred over Avalonia after those measurements.
6. The exact installed paths for the editor and backend.

### 12.3 Downstream passes (informational)

- **P3** — read-only backend projection and protocol host.
- **P4** — draft validation and diagnostics.
- **P5** — atomic save, revision check, mutex, concurrency tests.
- **P6** — WPF read-only canvas.
- **P7** — editing interactions.
- **P8** — preview/save UX.
- **P9** — packaging/installer integration.
- **P10** — hardware/guest acceptance, including D1–D6.
- **P11** — hardening, docs, release decision.

The pass numbers are planning units, not authorization. Each pass needs its own gate.
