## 3. Restoration procedure — established and verified BEFORE the change

Restoration was proven before the authorised rearrangement, not after it:

1. Baseline snapshot captured to JSON (paths, source/target ids, mode indices, monitor rects,
   work rects, primary flags, refresh, output technology).
2. `-Verify` against that snapshot returned `matches: true`, `mismatches: []`.
3. The write path validates the requested topology with `SDC_VALIDATE` before `SDC_APPLY`,
   so an invalid topology can never be applied.
4. `-Restore` replays the recorded source positions by `sourceId`/`targetId` match, then
   re-verifies.

Two implementation findings worth recording, because both silently produce a "successful"
no-op:

- **In the tested data representation, PowerShell did not write through nested struct
  members on array elements.** With a strongly typed .NET array of sequential-layout structs
  accessed in-process via PowerShell's member binder, mutating
  `$modes[$i].sourceMode.position.x` silently discarded the write, and the
  `$element = $arr[$i]; $element.x = …; $arr[$i] = $element` copy-back form also did not
  persist for the nested (`struct`-within-`struct`) member. This observation is scoped to
  that representation (array-of-struct with a nested struct member, PowerShell 7 on .NET,
  x64, in the same runspace that allocated the array) and to this execution path. It is
  **not** a general claim that PowerShell cannot mutate structs: direct assignment to a
  non-nested field, and assignment through a variable holding a `[ref]`-like wrapper, are
  different cases and were not exhaustively tested. A minimal reproduction was run in
  isolation and reproduced zero-write for the nested case. Because of this, all CCD mode
  mutation was moved into compiled C# helpers, which removed the class of failure entirely.
- `ChangeDisplaySettingsEx` reported `DISP_CHANGE_SUCCESSFUL` yet produced no change on this
  hybrid-GPU host. The CCD API (`SetDisplayConfig` with supplied paths/modes) was the only
  path that actually moved a display. This is a host-specific observation, not a general
  rule.
- `DisplayConfigGetDeviceInfo` returns Win32 error 31 here, so CCD cannot supply the
  identity strings. Identity correlation therefore uses the GDI monitor device id
  (`MONITOR\LGD0615\…`) plus the source-mode size and output technology.

## 5. Fixture and resolution rules

Disposable fixture (never the real config), item `d2-internal-relative`:

```json
"layoutMode": "relative",
"layoutRelative": {
  "monitor": { "identity": "path:LGD0615/<instance-redacted>" },
  "basis": "workArea",
  "rect": { "x": 0.5, "y": 0.5, "w": 0.5, "h": 0.5 }
},
"layout": { "x": 100, "y": 100, "w": 800, "h": 600 }
```

Applicable rounding rule (`ConvertTo-DevWSRelativeAbsoluteRect`): edges are computed first,
each edge is rounded with `MidpointRounding.AwayFromZero`, and width/height are **derived
from the rounded edges** afterwards; a valid target is at least 1×1.

Basis = internal work area `-1920,355 1920x1040`:

| Edge | Raw | Rounded |
| --- | --- | --- |
| left | `-1920 + 0.5·1920 = -960` | `-960` |
| right | `-1920 + 1.0·1920 = 0` | `0` |
| top | `355 + 0.5·1040 = 875` | `875` |
| bottom | `355 + 1.0·1040 = 1395` | `1395` |

Expected resolved rect: **`-960,875 960x520`**. No rounding step modified any value here,
so this case does not by itself exercise the rounding rule; it does exercise negative-coordinate
preservation end to end.

distinct serialization and rendering paths (protocol response for `project`, protocol
response for `preview`, and WPF canvas placement), not independent agreement of the geometry
algorithm.

### 8.1 Limitation: no independent before/after window inventory

**No independent before/after inventory of user windows was captured.** The display
rearrangement therefore cannot be shown to have left every pre-existing user window
untouched.

What is known:

- No DevWS-managed fixture window was launched during this pass; the installed lifecycle was
  not exercised, so no managed window was created, moved or closed.
- The only windows this pass intentionally created were the editor smoke window and the
  temporary scheduled-task runner. Both were closed, and post-run checks confirmed no editor
  or backend process remained (`editors=0`, `genuineBackends=0`).
- Full-desktop screenshots were captured during the negative-origin phase and again after
  restoration (whole virtual desktop plus one per screen). None of these was archived: the
  raw captures contained unrelated user windows, so only **derived topology diagrams** and a
  cropped DevWS editor-window capture were published. They were taken **after** each change,
  not before it, so they are not a before/after window comparison and cannot prove that no
  window moved.
- Windows can be displaced when a display is rearranged, and the operating system may
  relocate or minimise windows that were on the moved panel. The negative-origin phase
  lasted roughly 19 minutes (`14:00`–`14:19` local capture window), which is long enough
  for such effects.

What is **not** established, and should not be claimed:

- that every user window retained its original position;
- that no user application was closed or restarted by the display change.

No such closure or displacement was **observed**, but the absence of an observation is not
evidence of absence: there was no tracking process, and no per-window HWND snapshot was
recorded before the change. This limitation is recorded rather than claimed as a pass. A
future physical pass should capture a window inventory (HWND, PID, rect) immediately before
and after the change.

**D3–D6 remain NOT QUALIFIED.**

### Recommended path to close the installed-lifecycle gap

In priority order:

1. **Scoped guest reported to support a negative-origin display (feasibility hypothesis,
   not established).** The proposal is that a disposable Hyper-V guest could present two
   virtual displays and that the guest could arrange one at a negative X, keeping the elevated
   broker and tasks entirely inside the guest — the same isolation shape as the P9-BR2 D1
   replay that already passed. **This is a hypothesis requiring demonstration, not a verified
   capability.** It was *not* tested in P9-C: no guest was created, started, or connected to.
   Whether a guest can actually present a second display with a genuine negative origin —
   and whether it does so through VMConnect Enhanced Session Mode (`mstsc /multimon`,
   `selectedmonitors:s:`) or only through a conventional RDP session — is an open question.
   P9-D investigates this specifically. Needs supervisor approval for a guest envelope before
   any execution.
2. **Parameterise the privileged root and task names.** Make `Get-DevWSPrivilegedInstallRoot`
   and `Get-DevWSScheduledTaskNames` derive from the product identity (the bootstrapper already
   carries `ProgramFilesRootLeaf`/`InstallRootLeaf`), plus a distinct broker pipe name. This is
   product work and must not be started in this phase; it would make same-host fixture installs
   genuinely isolated for all future hardware passes.
3. **Documented production-repair acceptance.** Only if 1 and 2 are rejected: back up the
   privileged root, tasks and config, run the installed lifecycle test against a fixture
   account, then restore and hash-verify. Rejected as a default because it temporarily
   modifies production state on the owner's working machine.

Option 1 would be the lowest-risk route **if its premise holds**, but the premise is
unproven and must be demonstrated before it can be relied on.
