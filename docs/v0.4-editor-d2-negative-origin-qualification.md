## 3. Restoration procedure — established and verified BEFORE the change

Restoration was proven before the authorised rearrangement, not after it:

1. Baseline snapshot captured to JSON (paths, source/target ids, mode indices, monitor rects,
   work rects, primary flags, refresh, output technology).
2. `-Verify` against that snapshot returned `matches: true`, `mismatches: []`.
3. The write path validates the requested topology with `SDC_VALIDATE` before `SDC_APPLY`,
   so an invalid topology can never be applied.
4. `-Restore` replays the recorded source positions by `sourceId`/`targetId` match, then
   re-verifies.

Two implementation findings worth recording, because both silently produce a "successful"
no-op:

- **PowerShell cannot write through nested struct members on array elements.** Mutating
  `$modes[$i].sourceMode.position.x` silently discards the write, and even
  `$element = $arr[$i]; $element.x = …; $arr[$i] = $element` did not persist for nested
  members. All mutation therefore happens inside compiled C# helpers.
- `ChangeDisplaySettingsEx` reported `DISP_CHANGE_SUCCESSFUL` yet produced no change on this
  hybrid-GPU host. The CCD API (`SetDisplayConfig` with supplied paths/modes) was the only
  path that actually moved a display.
- `DisplayConfigGetDeviceInfo` returns Win32 error 31 here, so CCD cannot supply the
  identity strings. Identity correlation therefore uses the GDI monitor device id
  (`MONITOR\LGD0615\…`) plus the source-mode size and output technology.

## 5. Fixture and resolution rules

Disposable fixture (never the real config), item `d2-internal-relative`:

```json
"layoutMode": "relative",
"layoutRelative": {
  "monitor": { "identity": "path:LGD0615/<instance-redacted>" },
  "basis": "workArea",
  "rect": { "x": 0.5, "y": 0.5, "w": 0.5, "h": 0.5 }
},
"layout": { "x": 100, "y": 100, "w": 800, "h": 600 }
```

Applicable rounding rule (`ConvertTo-DevWSRelativeAbsoluteRect`): edges are computed first,
each edge is rounded with `MidpointRounding.AwayFromZero`, and width/height are **derived
from the rounded edges** afterwards; a valid target is at least 1×1.

Basis = internal work area `-1920,355 1920x1040`:

| Edge | Raw | Rounded |
| --- | --- | --- |
| left | `-1920 + 0.5·1920 = -960` | `-960` |
| right | `-1920 + 1.0·1920 = 0` | `0` |
| top | `355 + 0.5·1040 = 875` | `875` |
| bottom | `355 + 1.0·1040 = 1395` | `1395` |

Expected resolved rect: **`-960,875 960x520`**. No rounding step modified any value here,
so this case does not by itself exercise the rounding rule; it does exercise negative-coordinate
preservation end to end.

## 9. Verdict

**D2 editor layer = PASS**, scoped to this hardware and this one arrangement change:

- verified physical negative-X topology (three independent observations);
- correct `path:`-identity monitor selection, not ordinal/role;
- correct authoritative relative-layout resolution;
- matching editor `project`, `preview` and canvas coordinates;
- no clamping of negative coordinates;
- no unauthorised production interaction;
- full restoration of the original topology and configuration.

**D2 installed lifecycle placement = NOT QUALIFIED.** The remaining gap is unchanged and
explicit: placing a real managed window at negative coordinates through the installed CLI
requires the elevated broker path, which on this host is the production privileged runtime
and production task names. That was out of scope and was not attempted.

**D3–D6 remain NOT QUALIFIED.**

### Recommended path to close the installed-lifecycle gap

In priority order:

1. **Scoped guest with a real negative-origin display (recommended).** A disposable Hyper-V
   guest can be given two virtual displays; recent Windows guest drivers allow arranging the
   second at a negative X. This keeps the elevated broker and tasks entirely inside the guest,
   exactly like the P9-BR2 D1 replay that already passed. Needs supervisor approval for a new
   guest envelope.
2. **Parameterise the privileged root and task names.** Make `Get-DevWSPrivilegedInstallRoot`
   and `Get-DevWSScheduledTaskNames` derive from the product identity (the bootstrapper already
   carries `ProgramFilesRootLeaf`/`InstallRootLeaf`), plus a distinct broker pipe name. This is
   product work and must not be started in this phase; it would make same-host fixture installs
   genuinely isolated for all future hardware passes.
3. **Documented production-repair acceptance.** Only if 1 and 2 are rejected: back up the
   privileged root, tasks and config, run the installed lifecycle test against a fixture
   account, then restore and hash-verify. Rejected as a default because it temporarily
   modifies production state on the owner's working machine.

Option 1 is the lowest-risk way to close the gap without touching this machine's production
installation.
