Two documentary corrections were applied before the merge, and the overall verdict
(**guest feasibility NOT ESTABLISHED**) was preserved:

1. **Contiguity corrected.** Win32 defines a contiguous arrangement geometrically — "each
   monitor touches another monitor on at least part of one edge". The host's panels share an
   edge, so the arrangement **is** contiguous. Non-consecutive monitor IDs `0` and `3` are
   **not** evidence of non-contiguity, and the earlier draft was wrong to imply it. What stays
   untested is RDP's own acceptance behaviour for that ID list.
2. **Remote display driver corrected.** A remote terminal is served by a **WDDM remote
   Indirect Display driver**, and "the WDDM remote driver can expose **up to 16 monitors** to
   the remote session" (`consoles-vs-terminals`). One console display adapter is therefore
   **not** an inherent blocker to multiple RDP session monitors. Console displays belong to the
   console terminal and are not enumerated in a remote session. What stays untested is whether
   two selected client displays actually enumerate as two guest monitors here.

## 2. Resource gate — measurement and verdict

The supervisor required **at least 10 GiB available RAM** before provisioning, with explicit
prohibitions on freeing memory by terminating, suspending, or closing the owner's applications.

### Measurement method

Two independent counters, sampled repeatedly to exclude a transient dip:

- `Win32_PerfRawData_PerfOS_Memory.AvailableBytes` — the amount available for allocation,
  including standby pages that can be repurposed.
- `Win32_OperatingSystem.FreePhysicalMemory` — free physical memory.

physical 31.86 GiB.

**Observed range: 4.30–4.69 GiB available. Required: 10 GiB.**

### Verdict

**RAM_GATE_PASS = false.** The shortfall is 5.3–5.7 GiB. This is not a marginal miss and not a
sampling artifact: every sample is below half the requirement.

### Cause

The deficit is structural, not incidental:

| Consumer | Memory |
| --- | --- |
| `DevWS-v0.3.0-C2-Acceptance-20261102` (protected, **Running**) | **8.0 GiB assigned** |
| Owner applications (Firefox instances, Discord, ChatGPT, Antigravity, opencode, etc.) | several GiB |
| Windows itself (DWM, Defender, Memory Compression, services) | remainder |

The only sizeable, immediately reclaimable block is the **8 GiB assigned to a protected
acceptance VM** — which this pass is explicitly forbidden to stop, along with the owner's
applications. Even if that VM were stopped (it was not, and will not be without authorisation),
the ceiling would be roughly 12.5 GiB, which would just clear the gate but would itself be an
unauthorised action against a protected resource.

## 5. What execution would require

To run P9-E as designed, one of the following must change — each needs supervisor decision:

1. **Free memory within the rules.** The gate cannot be met while the protected C2 VM holds
   8 GiB and the owner's applications are running. If the supervisor authorises stopping that
   specific acceptance VM for the duration (it is the only large reclaimable block), the gate
   is plausibly satisfiable. Stopping it was **not** done here because protected resources are
   out of scope without explicit approval.
2. **Lower the gate with a smaller guest.** A 2 GiB-startup guest with a 3 GiB ceiling might run
   in the available memory, but that weakens the guest envelope the supervisor specified
   (4 GB startup) and increases the risk of a flaky session confounding E1/E2 evidence. Not
   recommended as evidence-grade.
3. **Run P9-E on a different host** with adequate free memory.
4. **Defer P9-E** and close the D2 lifecycle gap by product work instead — parameterising the
   privileged root, task names, and broker pipe name so a fixture installation can coexist with
   production on one machine. This needs no guest and no display change, but it is product
   change and must not be started inside a documentation phase.
